# 清楚、好读的图文交付

目标：让读者先明白结论，再看懂结构、过程或行动安排。成品必须讲人话；漂亮版式不能补救难懂的内容。

## 先判断是否值得生成

按请求的意思和预期内容判断，不靠关键词、字数或“有一个表格”机械决定。

| 读者需要理解什么 | 合适的交付 |
| --- | --- |
| 系统由谁组成、谁负责什么、怎样配合 | 架构介绍：一张总览，必要时再加一张流程图 |
| 一个过程怎样发生、分支如何选择、异常怎么处理 | 机制讲解：流程或时序图，加一个具体例子 |
| 接下来怎么做、先后依赖、完成后得到什么 | 分阶段计划：阶段路线、验收、依赖与风险 |
| 多个方案如何取舍 | 方案比较：围绕少量决策标准比较，给出建议及条件 |
| 一份要转发、归档或复用的较完整说明 | 独立图文文档；保留事实依据和适用范围 |
| 一个事实、一个术语定义、当前状态、一条命令 | 直接在聊天回答 |
| 围绕已有文档问一个局部问题 | 就地解释并指向相关部分；不重建整篇 |

明确要求“不要图、文字就行、只说一句”时按用户要求。明确要求文档或图时按请求交付。
不在表中的请求，用同一判断：图形或排版能否让关系、顺序、取舍或行动更容易理解？能就生成合适规模的文档；不能就简洁回答。

架构介绍不必写成长篇，机制讲解不必强塞流程图，计划没有真实日期就用阶段和依赖，不编造时间表。

## 写作先过一遍“人能读懂吗”

1. 开头用一两句话回答用户的问题，说明这份内容能帮助他理解或决定什么。
2. 按读者的问题组织内容：谁做什么 → 信息怎么走 → 为什么这样安排 → 边界或下一步。
3. 每段讲一件事，使用具体主语和动作。把“完成状态物化与生命周期治理”改成“把结果写入任务库，让重启后还能查到”。
4. 术语第一次出现就用一句话解释。正文用容易理解的角色名；代码名、API和路径只在有助核对时出现，集中放在证据或实现说明里。
5. 图后解释读者应该注意什么，不能让读者自己猜箭头。使用一个小例子帮助理解抽象机制。
6. 计划写清做完会得到什么、先做什么、怎样验收；不要只罗列任务编号。
7. 分开已验证事实、建议与未确定事项。不要用圆满措辞掩盖未上线或未验收。

交付前设想：一个了解业务但没读过代码的人，能否在半分钟内说出结论，随后顺着正文理解原因？不能就先改文字。

## 按内容选结构

使用 [delivery-patterns.md](references/delivery-patterns.md) 的架构、讲解、计划、比较结构作为起点；不必填满所有栏目。
图的写法见 [mermaid-authoring.md](references/mermaid-authoring.md)。事实从当前代码、权威文档或用户材料取，不凭图形补齐未知模块。

正文写 Markdown：`# 标题`，紧跟 `> 一句话结论`，小节用 `##`。Mermaid 围栏只用于真正有关系或过程需要解释的图。

## 使用现有渲染器

```bash
python3 tools/arch_doc.py source.md -o output/ --width 1100
```

在本体仓目录可用上面的命令；业务工作目录中使用 hook 提供的 renderer 绝对路径，或调用技能的 `scripts/render_doc.sh --engine-root <本体目录> source.md -o output/`。不要把渲染器复制进业务仓。依赖和实际产物格式以工具 `--help` 为准。
HTML 应完整、自包含。长内容可以拆成连续 PNG 页，聊天先给可读预览，再附完整文档；不要把整份长文压成一张无法阅读的小图。
`--png-only` 也必须使用最新 Markdown；旧文件存在不代表本次生成成功。

## 两道质量检查

**机械检查**：全部图成功渲染，错误 Mermaid 必须报错；目录链接有效；正文完整、不溢出、不截尾；产物确实来自这次源文。检查本次输出清单和渲染报告。

**视觉与阅读校样**：逐页查看实际 PNG。发现问题先核对，再改写或调整版式：

- 字号清楚、层级明确，阅读顺序自然，空白不过多也不拥挤。
- 图中节点短、箭头有意义、分组清楚；宽图被缩成小字时拆图。
- 同一标题或摘要不重复三遍，正文里不露出 Markdown 符号。
- 表格用来比较或映射，解释仍写成顺畅的段落；长表拆成读得懂的部分。
- 色彩表达角色或状态，不能只靠颜色区分含义；代码与正文有清楚区别。
- 看过图后能读懂正文，读完正文也能解释图；不使用只有作者知道的代号。

视觉模型对“缺了某个标题、少了某个节点”的判断，先用DOM或源文核实；不能核实时不照着乱改。它对拥挤、对比度、文字太小的反馈用于实际校样。
图存在、SVG数量正确，仍不代表图易读；检查器通过也不能代替阅读。

## 交付

聊天给一两句话结论、可读预览和完整HTML；多页图按顺序提供，不再贴一整份Markdown副本。
不在封面或页脚泄漏绝对路径、用户名、凭据或内部环境细节。需要实现证据时按交付范围使用合适的相对引用。
无法完整渲染时明确报错或降级，不用旧PNG冒充新产物，不把未校样说成效果已保证。

## 验证与安装

修改后运行渲染回归、触发场景测试，并对至少一份架构、一份机制解释和一份计划实际出图校样。
源技能与已安装技能可能不同：先比较，保留有效修正、备份现场副本，再只更新本技能；不要借机重写整个profile配置或其它技能。
