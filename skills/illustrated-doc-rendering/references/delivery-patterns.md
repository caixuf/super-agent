# 按读者的问题组织文档

这些是起点，不是必须填满的模板。每份文档只回答当前问题，避免把所有实现细节都塞进去。

## 架构介绍

读者通常想知道：这套系统做什么、由谁完成、一次请求怎么走、哪些地方不能混。

建议顺序：一句话用途 → 主要角色总览 → 一次请求的旅程 → 两三个重要边界 → 进一步核对的依据。
总览图控制在约四到八个主要节点，用角色和动作命名。模块细分另画局部图；不要把全仓目录树画成连线图。
“任务库”先解释成“保存进度和结果，重启后还能接着查”，需要时再补数据库名称。

## 机制讲解

读者想知道：它怎样工作、为什么能解决问题、在什么条件下失效。

建议顺序：直接回答 → 三到五步过程 → 一个具体例子 → 例外与适用条件。
有明确交互双方和等待顺序时用时序图；有决策分支时用流程图；只有一两步时可以不画图。
引用一个小的真实或明确标注为假设的例子。不要把“先发生”写成“因此导致”，不要把“请求取消”写成“已经停下”。

## 分阶段计划

读者想知道：完成后得到什么、现在先做什么、怎样确认做完。

建议顺序：目标与当前起点 → 三到五个阶段 → 每阶段的可见结果与验收 → 依赖和主要风险 → 紧接着的一个动作。
阶段名称写用户能理解的结果，例如“让后台任务真正独立运行”，而不是只写编号。
没有承诺日期时用依赖路线，不生成假日期的甘特图；并行工作如实并行，不为图好看而伪造先后关系。

## 方案比较

读者想知道：按什么标准选、各自适合谁、建议在什么条件下成立。

先给建议及条件，再用三到五个真实相关标准比较，最后说明关键代价与未确定项。
少量比较可以直接放在聊天，不必每个两列表格都生成附件。不要给没有依据的精确打分。

## 交付前的语言检查

- 第一段是否已经回答问题？删除铺垫和泛泛介绍。
- 每个抽象名词能否换成“谁做什么、产生什么结果”？
- 术语是否解释过？一句话里是否同时塞入太多代码名？
- 图是否减少了理解成本？若只是重复目录，删掉或重画。
- 计划是否能据此开始做事，而不仅是“完善、优化、提升”？
- 边界、证据和未知项是否准确，而不是堆在结尾的一段空泛声明？
