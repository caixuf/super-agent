# 各家 IM 怎么做「流式回复」：三种实现与取舍

用途：决定“这一轮走卡片还是纯文本”，或向用户解释为什么这条路这么难。
结论先行：业界只有两三种做法，**难点不在渲染，而在“谁负责终稿”**。

## 三种主流实现

| 平台 | 机制 | 关键约束 |
| :--- | :--- | :--- |
| IM 平台 | **CardKit 卡片实体**：`POST /cardkit/v1/cards` 建实体拿 `card_id` → 发消息只引用 `card_id` → 之后原地推 `/cards/{id}/content`，终稿用最后一次更新定格 | 卡 JSON 必须 2.0；`sequence` 严格递增；同卡 10 次/秒；客户端 ≥7.20 |
| Slack | `chat.startStream` → `appendStream` → `stopStream` | 流对象生命周期必须闭合，否则消息留在“生成中” |
| Telegram | 只能 `editMessageText` 反复改同一条 | 有速率限制，长回答会限流，公认体验最差 |

IM 平台还有一条**旧路**：`PATCH /im/v1/messages/{id}` 直接改消息。它有一个隐性编辑次数上限（实测约
20–30 次），**超限后接口仍返回成功但内容不再更新**——表现为“卡片停在某一帧”或“长回答只见开头”，
日志里一句错都没有。高频流式不要走这条路。

## IM 平台 CardKit 要点

```json
{"schema":"2.0",
 "config":{"streaming_mode":true,
           "streaming_config":{"print_frequency_ms":{"default":70},
                               "print_step":{"default":1},
                               "print_strategy":"fast"}},
 "body":{"elements":[{"tag":"markdown","content":"…","element_id":"md1"}]}}
```

- 发消息时传 `{"type":"card","data":{"card_id":"…"}}`，**不要**再传整卡 JSON；
- 每帧带递增 `sequence` + 稳定 `uuid`，否则服务端丢帧且不报错；
- 流式期间客户端回调不会被立即处理，交互按钮要在终稿后再挂；
- 卡片实体有容量上限，长会话要按 TTL 回收实体，否则创建被拒。

## 取舍：卡片 vs 纯文本

- **卡片**：有打字机效果、可挂按钮、表格渲染更好；代价是整条链路更脆（实体创建、序列、频率、终稿归属），
  任一环失败都可能是**静默**的。
- **纯文本**：最稳，失败时有明确错码；放弃流式观感和按钮。
- 判据：需要频繁交互/按钮 → 卡片；只需要把话说清楚、且有人在等结果 → 纯文本更划算。
  两者混用（卡片流式 + 宿主再补一条终稿）是最坏组合，见 SKILL.md 第五节。

## 现成实现怎么选

用户说"这个效果不错，有没有更稳的"时，先分清"渲染得好"与"归属没冲突"，再给名单：

| 实现 | 覆盖范围 | 适合谁 |
| :--- | :--- | :--- |
| `larksuite/channel-sdk-python` | 官方渠道 SDK：事件监听、消息归一、出站发送、媒体、卡片回调、流式回复 | 愿意按它的接口改造宿主，换取官方维护 |
| `larksuite/oapi-sdk-python` | 官方底层 SDK，只做 API 封装 | 自己实现实体、序列、节流 |
| `kaisleung96/feishu-streaming-card` | 轻量 CardKit 封装：建实体、推内容、终稿换彩色卡，约十行调用 | 快速接 CardKit、不绑定特定宿主 |
| Hermes 专用的 HFC（`baileyh8/hermes-feishu-streaming-card`） | 宿主 hook + 常驻 sidecar + CLI + 验收门 | 已在 Hermes 上，且接受单一组件独占发送 |

三条判据：

- **稳定性来自归属唯一，不来自库本身。** 只负责"渲染"、让宿主继续补终稿的库，无论换哪家都会复现覆盖/丢失。
  选型先问一句：它是否独占"发送 → 更新 → 终稿 → 回调"整条链路。
- **带 sidecar/hook 的实现要装两处**：宿主 venv 与它自己的 venv，两边同名模块哈希必须一致（见 SKILL.md 第六节）。
- **没定位归属层就换库，等于搬一次家。** 先用 `Normal final-send NOT suppressed` 这类日志证明是哪一层在发，
  再谈替换；否则新库只是把旧冲突换个地方复现。

## 自检

- 用户说“长回答看不到 / 只看到开头”：先数这一轮的更新帧数，接近 20–30 就要怀疑编辑次数上限；
- 用户说“闪一下就没了”：查宿主是否把首发预览当旧消息删了；
- 用户说“整卡请升级客户端”：查卡是不是 2.0 发给了低于 7.20 的客户端。
