### 已确认需要修的点

1. `tools/arch_doc.py:350`：`--png-only` 在已有同名 HTML 时跳过重新渲染。Markdown 改了，PNG 仍可能截旧 HTML。应每次从当前输入生成临时 HTML；`--png-only` 只控制交付物，不控制是否读取最新源文。
2. `tools/arch_doc.py:318`：固定默认高度 4200。`trim()` 只能裁白，不能证明底部未被截断。应在渲染完成后测量正文实际高度，再完整截图；超出浏览器限制则拆图或明确失败，不能报成功。
3. `tools/arch_doc.py:42`：浏览器列表带固定宿主用户路径。应按环境变量覆盖、PATH、当前用户目录顺序发现。现有脚本在本机能用不代表新机能复现。
4. `tools/arch_doc.py:284-287`：截图仅检查目标 PNG 是否存在，未保证本次成功生成。旧 PNG 存在时，浏览器失败可能被当成功。应写临时目标、检查退出码和文件、验证完成后原子替换。
5. `tools/arch_doc.py:193`：图块统计只识别无缩进的精确开围栏，和 `mermaid_to_div()` 支持的形式不一致。应共用解析规则，避免页脚计数与机械判据不一致。
6. `load_mermaid_script()` 仍允许 CDN 回退，而技能要求自包含。离线交付应要求已下载 vendor；无法内联时明确失败或显式标注降级，不能自称离线可用。

### 现有补丁到底做了什么

- `patches/feishu_card_replies.patch`：只在 `metadata.expect_edits` 为真时创建交互卡片，随后 `edit_message()` 对已登记卡片走 PATCH；终稿直接发送仍走 post/text。这证明“可以改卡片”，不等于“全回合同一卡片”。
- `adapter.py:1795-1813`：PATCH 成功且 `finalize=true` 时会移除卡片登记。把工具边界当成终态，会让后续编辑失去卡片类型信息。
- `patches/card_preview_bubble_cleanup.patch`：终稿另发后删除旧预览，只能减少残留气泡，不是保持消息身份。
- `gateway/run_turn.py:739-784`：生产构建 consumer 配置时，fresh-final 时间阈值只对 Telegram 开启，其他平台是 0。不要误把这个通用分支认作本平台当前换卡的根因。

### 真正需要改的几个点

1. **工具边界语义**：`gateway/stream_consumer.py:827-848` 会在 segment break 时传 `finalize=true`；`:925-941` 对 edit transport 重置消息状态。若没有平台能力区分，每次工具调用后都可能重新开消息。
2. **持续消息能力**：`_cumulative_transport():909-913` 当前只含 draft/native。应增加显式、默认关闭的平台能力来保留同一 message ID；不要全局改成所有 adapter 都累计。
3. **终态与段落结束分开**：既要保留 message ID，也不能让工具边界提前摘掉“运行中”或移除卡片登记。需要把 `is_turn_final` 语义传到卡片编辑边界，而不是只改 `_end_segment()` 一行。
4. **相同正文也要封口**：`gateway/stream_consumer_transport.py:478-483` 对正文未变的编辑会短路；适配器应支持真正的终态更新能力。不能只依靠最后 token 不同来移除“运行中”。
5. **可靠送达判据**：只有终态 PATCH 成功后才设置 delivered/suppression 标志。超时属于结果不明，不能盲目再发一张卡；明确拒绝可走受控降级。卡片失败不能伪装成已交付。
6. **范围与上限**：超长正文、附件、审批、取消、平台限流必须定义行为。正文超限时可保留一张摘要卡并附文档；不要承诺平台硬上限之外仍塞进一张卡。

### 最小验收矩阵

| 场景 | 必须观察到的证据 |
| --- | --- |
| 普通流式回复 | 首次发送 1 次；后续只编辑同一 message ID；终态 PATCH 成功 |
| 工具调用两次 | segment break 不更换 message ID；中途不被误标完成 |
| 最后正文与上一帧相同 | 仍有终态更新；运行提示结束 |
| 没有任何 token 的任务 | 明确展示等待/失败/完成，不留下永久运行卡 |
