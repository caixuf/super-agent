# T5 交互形态设计：任务卡句柄 + 尺度路由（2026-10-26）

> 定位：**T5（平台 adapter 与 stream finalize 协议）** 的设计指导。
> 任务板原文口径：*一任务一消息 ID，阶段更新和终稿均更新同一 ID；失败不另发伪终稿；需平台真验*。
> 本文把它从「怎么把卡片刷得好看」改写为「**交互形态**」——因为前者是在错误结构上打磨。
> 本轮**未改任何生产代码、未重启服务、未发外部消息**；参考实现见 `agentcore/task_card.py` 与其测试。
>
> 平台名在本文用 `Feishu`（本仓适配层名，见 `patches/`）；领域词一律用占位符。

---

## 0. 判断：错不在"流式"，错在把三种时间尺度塞进了一个"会动的消息"

聊天是**回合制、易失、线性滚动**的；而这个 agent 干的活是**长时、有状态、有产物**的。
把长活塞进"一条不断被重写的消息"，就会同时冒出：秒数焦虑、终态被盖、要删预览条、重启即失联。
这些不是 bug，是**载体与负载不匹配**的必然产物。

而用户其实在做**四件性质完全不同的事**：

| 用户在做的事 | 时间尺度 | 现在被当成 | 应该被当成 |
| :--- | :--- | :--- | :--- |
| "任务跑完没" | 秒级 | 一次模型回合 | **确定性查表，秒回** |
| "跑一下这个需求" | 分钟级 | 一条刷秒数的卡 | **认领 + 完成通知** |
| "为什么挂了" | 对话级 | 同上 | **真流式推理** |
| 看结果 | —— | 聊天里贴正文 | **指向产物** |

四种共用一套"更新中的卡片"，所以每种都不好用。

## 1. 交互形态：三个原语

### ① 任务卡 = 一任务一卡片的**稳定句柄**（不是"进度条"）

卡片是**对象**，不是"消息的临时状态"。它出生即创建、跨进程/重启保持同一 ID、有明确终态、终态后不再变。
它是**结构化**的，不是文本 blob：

```
┌──────────────────────────────────────────────┐
│ 🧪 跑用例 · 掉头 全量                  [代际]  │  ← 对象 + 代际徽标，不变
├──────────────────────────────────────────────┤
│ 状态   ⏳ 运行中 · 第 3 分钟                  │  ← 只在跃迁时变，不刷秒
│ 阶段   编译 matcher → 用例 8/14               │
│ 宿主   node-a · runner-03                     │  ← 谁在跑（派工透明）
│ 产物   —（完成时这里长出报告链接）             │
├──────────────────────────────────────────────┤
│ [ 取消 ]   [ 详情 ]   [ 看日志 ]              │  ← 动作，不是"引用回复"
└──────────────────────────────────────────────┘
```

### ② 按**时间尺度**路由，而不是按"有没有话说"

- 秒级确定性问题 → **直接答，不建卡、不烧模型**。
- 长任务 → **"跑完叫你"**。认领后卡片进入运行态，中间**不刷屏**，只在**阶段跃迁**和**终态**更新。
- 对话/调试 → **唯一真正值得流式**的场景：模型在*推理*，"边想边说"能降等待焦虑、还能让用户中途纠偏。

### ③ 聊天只做信使

触发、通知、短问答留给聊天；**状态和产物指向它们该在的地方**——平台 web UI、报告、任务板。

## 2. 任务卡句柄契约（参考实现：`agentcore/task_card.py`）

### 2.1 生命周期与状态机

```
QUEUED ──▶ RUNNING ──▶ DONE        （终态）
                    ├─▶ FAILED      （终态）
                    └─▶ CANCELLED   （终态）
```

**终态是写一次的**：一旦 `DONE/FAILED/CANCELLED`，后续任何帧一律**丢弃**。
这正是「失败不另发伪终稿」与「终态不被迟到帧覆盖」两条口径的机制化——不是靠调用方自觉。

### 2.2 三条硬规则（都由 `CardWriter` 强制）

| 规则 | 机制 | 挡住的故障 |
| :--- | :--- | :--- |
| **顺序** | 每张卡一个 `sequence`，**严格递增**；`<=` 已处理的帧丢弃 | 乱序/迟到帧回退卡片 |
| **幂等** | 每帧 `uuid = f"{task_id}:{sequence}"`，重复 uuid 丢弃 | 重试导致重复应用 |
| **终态锁** | 终态后所有帧丢弃 | 迟到的进度帧盖掉"✅ 完成" |

**单一写者**：一张卡同时只有一个 `CardWriter` 在发。任何旁路直发一律禁止——
线上事故的根因就是旁路更新不受管、last-write-wins。

### 2.3 持久化（本契约的**宿主责任**）

`task_id → CardHandle(chat_id, message_id, sequence, state, started_at)` **必须落宿主任务库**，
不能只放 adapter 进程内存。理由：worker/网关重启后仍要能更新**同一张卡**，而不是丢下它另开一张。

### 2.4 心跳：沉默即信息

宿主长时间没话说时，`heartbeat()` 推进一个 `RUNNING` 帧，让卡片**不冻结**。
用户看到的是"还在跑 3:12"，而不是一段停住的旧文案——**沉默必须仍然是有信息的**。

### 2.5 路由（`route()`）

从**信号**决策，不从措辞决策：

| 信号 | 结果 | 形态 |
| :--- | :--- | :--- |
| 确定性命中 | `LOOKUP` | 秒回，不建卡、不流式 |
| 预估 ≥ `LONG_JOB_SECONDS`(默认 20s) | `LONG_JOB` | 建卡 + 完成通知，**不流式** |
| 推理回合 | `CONVERSATION` | 流式回复 |
| 未知 | `CONVERSATION` | 短回复 |

## 3. 反直觉的几点（设计立场）

1. **流式在长任务上是反模式。** 它制造"很忙"的错觉——用户盯着卖萌语，实际什么都没得到。
   真正的体验是：**发起 → 去干别的 → 被 ping 回来**。把打字机用在 5 分钟的编译上，是好东西用错了地方。
2. **按钮 > 引用回复。** 现在"引用本卡片发「取消」"是个 hack——因为卡片回调没配。
   一次性配上 `card.action.trigger`，长期收益是：取消/详情/重跑/看报告都变成点一下，审批也能从纯文字升级回来。
3. **诚实的状态语义。** 要区分 **"我在想"**（模型推理，可流式）与 **"机器在跑"**（外部任务，是状态不是打字）。
   现在两者都渲染成"agent 正在打字"，用户分不清是卡住了还是在干活。
4. **产物不在聊天里。** 聊天适合触发/通知/短答；长内容与状态指向平台 web UI、报告、任务板。
5. **派工要透明。** 卡片上的"宿主/派给谁"那一行，把"主管 → 派给某台机的 runner"显式化。**看得见派工，才敢信任它。**

## 4. 落地：分两阶段

### Phase 1 — 确定性协议（零新依赖，**先做**）

1. `job_id → card_message_id` **落任务库**（不是内存/tmp）。
2. 单一写者 + 严格递增 `sequence` + 幂等 `uuid`（本仓 `agentcore/task_card.py` 即契约参考）。
3. **终稿即末帧**（`final=True` 走同一张卡），不另发新消息。
4. **失败发失败帧**，绝不伪"完成"；卡片更新本身失败 → **回落纯文本**，且不留半截卡片。
5. 阶段事件改走**网关结构化 `stream_events`**，不再读本机临时文件。
6. 路由按 §2.5 的信号表接进准入层。

### Phase 2 — 平台真流式（可选加速层，只换"文本增量"这一段）

平台若提供**卡片实体 + 流式文本元素**能力，则：

```
建卡片实体(streaming_mode=true) → 发一次(记 card_id → message_id)
  → 文本增量：推全量文本 + sequence 严格递增 + uuid
  → 结构变更（阶段行/步骤数）：按卡片级接口，与文本分开算 QPS 预算
  → 收尾：先关流式 → 全量更新终稿
```

要点/坑：
- **卡片实体只能发一次** → 天然契合"一任务一卡片"；重发 = 新卡片，禁止。
- 文本接口频率通常远高于卡片级接口（量级：数十次/秒 vs 十次/秒/实体）→ **客户端 100~200ms 合并**再推。
- 流式模式常带**自动关闭超时**（量级：10 分钟）→ 长任务需**心跳续开**或分段，`sequence` 继续递增。
- **处理卡片交互回调前先关流式**，否则回调期间更新会被拒。
- 客户端版本可能不支持 → **能力探测 + 降级**（探不到就走 Phase 1 的原地编辑）。
- **打字机只在"旧文本是新文本前缀"时出现**；前缀不一致则全量直接上屏。

> Phase 2 只改观感；**协议正确性不依赖它**。所以先做 Phase 1。

## 5. 必验故障场景（与 completion-guide 口径对齐）

| 场景 | 期望 |
| :--- | :--- |
| 重复 / 乱序帧 | `sequence` 回退帧被丢弃，卡片不回退 |
| 终稿后迟到进度帧 | **不覆盖终稿**（线上事故回归） |
| 卡片更新失败 | 回落纯文本，无半截卡片残留 |
| 任务失败 | 显示失败态，**绝不显示"完成"** |
| worker / 网关重启 | 能续上**同一** `card_message_id`（验证落库生效） |
| 长任务超过流式自动关闭超时 | 关流后仍能收尾（续开/降级） |
| 客户端不支持流式 | 降级到原地编辑，不报错不空白 |
| 卡片回调期间更新 | 先关流式，回调可正常处理 |

## 6. 边界与不做

- **不重启生产服务、不发外部消息**（除非用户显式授权并观察）。
- 物理仿真仍唯一走串行 FIFO 执行器；卡片只是**观测面**，不得成为执行路径。
- 卡片回调需平台应用订阅事件并配回调地址；**当前审批走纯文字**，不依赖回调——保持。
- 平台流式能力**不是安全沙箱、不是执行原语**；它只解决"同一张卡的文本怎么更新"。
- 本仓 `agentcore/task_card.py` 是**协议参考实现**（业务中立、零第三方依赖）；接到宿主 adapter / 任务库是下一步，本轮未接。
