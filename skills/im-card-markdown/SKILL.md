# IM 卡片渲染 Markdown：能渲染什么、在哪一版

## 技能定位

回答「这段 Markdown 放进卡片，会不会显示成源码」以及「卡片报错/半截渲染/时有时无时查哪一层」。
**不适用于**：纯文本消息（不需要卡片）、图文文档（那走渲染器出 HTML/PNG）。

## When to Use

- 回复要带表格/列表/代码块，不确定该用哪一版卡片结构；
- 卡片报 `200621` / `200861` / `200905`，或整卡「请升级客户端」；
- 用户说卡片“有时有、有时没有”“闪一下就没了”“只渲染一半”；
- 需要判断某个集成/sidecar/插件是不是当前唯一在发卡的那一层。

> 核心判据：**先确定卡片的结构版本，再决定用哪个文本组件；版本不对，内容再对也白搭。**

## 排查纪律（这类问题会拖成很长的链路，先立规矩）

卡片"不显示"是**多层**问题：发送、协议版本、网关清理、客户端版本各是一层，而且每层都能单独让
卡片消失。所以：

- **一次只证一层，证完就报**。不要去一次把四层同时查完再回复；用户等的是"现在到哪一步"。
  中间回复写成：已验证的事实 → 当前怀疑层 → 下一步怎么证，三句以内。
- **同一个结论不要推翻两次**。说"没发过卡片"之前先用消息列表 API 数清楚 `msg_type`
  分布；一张 `interactive` 都没数就直接断言"从未发过"，后面会被自己的数据推翻。
  推翻自己的前提是**新证据**（一个新的计数、一条用户给的观测），不是**新推理**——
  同一批日志换个解释就再说一遍"这次找到根因了"，是把猜测当发现，用户会跟着你绕圈。
- **假设被推翻后，要交的是分界证据，不是第四套解释。** 连续两套说法被用户否掉时，
  下一步不是换个机制再猜，而是在**同一个样本**上拉出"最后一个正确点 → 第一个错误点"：
  选用户明确说没收到的那一轮，把该轮的正文、事件、卡片创建、卡片更新、落库内容
  逐段对齐时间与 message_id，直到某个环节**之前内容正确、之后内容为空**。
  拿不到这条分界，就明说"证据不足，卡在 X 与 Y 之间"，不要给结论。
  聚合计数（`successes`/`failures`）只能证明某个组件自认为没出错，
  **无法定位断点**——用它推出来的因果链，用户一问时间线就露馅。
- **分清"我改了"和"生效了"**：改文件 → 语法检查 → 重启（PID 变）→ 真发一条 → 用户确认。
  中间任何一步都不能当成后一步已经完成。
- **不要否认自己刚做过的修改**。说"我没改过配置/没有这个开关"之前，先看生效配置的
  mtime：`stat -c '%y' ~/.hermes/config.yaml`。一次 `hermes config set` 就会把它刷成当前时刻，
  而对话里上一轮的动作很容易被忘掉。"我没改过"被 mtime 推翻，比诊断错本身更伤信任——
  用户会连带不再相信你后面所有的结论。

## 一、三套结构，各自能渲染什么

| 结构 | 文本组件 | 表格 | 列表 | 标题 | 代码块 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1.0（无 `schema`） | `div` + `text.lark_md` | ✗（显示竖线） | ✗（显示 `- x`） | ✗ | ✗ |
| 2.0（`schema: "2.0"`） | `markdown` 元素 | ✓ 原生 table 或 markdown 表格 | ✓ | ✓ h1–h3 | ✓ |
| card_components v2（客户端「2.4」） | `div` + `text.plain_text` | ✓ table 组件 | ✗ | ✗ | ✗ |

硬事实（实测）：

- 2.0 卡发到 v2 客户端会**整卡**降级成「请升级客户端」——所以要么全 2.0，要么别用 2.0；
- **`GET /im/v1/messages/<id>` 读回 2.0 卡永远返回那句占位符**（`{"tag":"img"…}` + 请升级文案），
  哪怕对方客户端正常显示；1.0 卡读回是真实结构。所以读回结果**不是** 2.0 卡的验收证据；
- 发送接口返回 `code: 0` 只证明卡片**被接收**，不证明**渲染**——两者必须分开确认；
- 纯 `plain_text` **不能**做独立元素，正文必须写成 `div` + `text.plain_text`，否则 `200621 type of element is not supported tag: plain_text`；
- 表格 `row_height: "auto"` 会被拒（`200905`）；用 `low/middle/high` 或像素值。

1.0 与 2.0 的 `markdown` 文本组件对代码围栏、`---` 分隔线、`>` 引用**都接受**（实测两边都 `code=0`）。
把这几样当成"卡片渲染不了"而把整条回复踢回 post，是没有依据的保守策略。

## 二、正文要“先过一遍能不能渲染”

```
如果含表格 / 列表 / 标题 / 代码块  → 必须走 2.0 的 markdown 元素
否则                              → 1.0 的 lark_md 更稳（宽度、字号按 1.0 调过）
```

判定要**按行判定**（表格 = 表头行 + 分隔行），不要只看有没有竖线字符。同一张卡里**不要放纯文本副本**：
markdown 元素与 plain_text 副本并存时，表格会被画两遍。

两个会"静默关掉整条卡片通路"的门槛错误，改判据时一起查：

- **门槛谓词过严**：宿主适配器若用正则把围栏/引用/分隔线列成「卡片表达不了」，任何带代码块的
  回复都退回 post —— 而卡片本来就能渲染。判据看的是"客户端显示得了吗"，不是"我实现起来麻烦吗"。
- **围栏内的竖线不是表格**：`awk -F'|' ...`、`| a | b |` 这类行在代码块里是**代码**。把它当表格
  抽成 table 元素，会把代码块撕成两段。表格识别必须先算每行是否在围栏内，围栏内的行一律跳过；
  分隔行计数同理，否则 "识别到的表格数 ≠ 分隔行数" 会让整条回复判成不可渲染。

自检一行：`card_renders_markdown("```bash\nls\n```")` 与 `card_renders_markdown("| a | b |\n|---|---|\n| 1 | 2 |")`
都应为 `True`。有 `False` 就是门槛写错了，不是内容不该进卡。

## 三、流式与更新

- 一条消息的卡片**结构版本不可变**：先发 1.0 就别想 PATCH 成 2.0，只能新发一条并把旧卡改成一句话指路；
- 一旦发的是 2.0 卡，后续阶段（图文、附件说明）**原地 PATCH**，不要再发新卡；
- PATCH 要求更新前后都是共享卡：`config.update_multi: true` 每一帧都要带。

**卡片会被网关自己的收尾清理删掉。** 流式路径把第一条预览的 `message_id` 记进待删集合，终稿以
"新消息"落地时按"替换旧预览"把那条删掉。卡片走的就是"首发预览 → 原地 PATCH"，于是会出现：
卡片先以 `interactive` 发出、两秒后终稿以 `post` 发出、卡片被删——用户看到"闪了一下就没了"，
而日志里一句错误都没有。

排查判据（不要凭"我没看到卡片"下结论）：

```bash
# 列出最近消息类型；出现 interactive 就是发过
curl -sS ".../im/v1/messages?container_id_type=chat&container_id=<chat>&page_size=50&sort_type=ByCreateTimeDesc" \
  -H "Authorization: Bearer $TOK" | jq -r '.data.items[] | "\(.create_time) \(.msg_type) \(.message_id)"'
# 单条读 body：content 恰为 "This message was recalled" 就是被撤回/删除
```

时序上"interactive 出现后紧接着一条 post"就是这个模式。修的方向是让卡片不被计入待删预览，
不是去改卡片结构。

## 四、报错速查

| 错误码 / 现象 | 含义 | 修法 |
| :--- | :--- | :--- |
| `200861 unsupported tag note` | 1.0 标签（note/markdown）出现在 v2 卡里 | 去掉或改 `div`+`plain_text` |
| `200621 ... tag: plain_text` | 裸 `plain_text` 元素 | 包成 `div` |
| `200905 table row height is invalid` | `row_height: "auto"` | 改 `low` |
| 表格画了、后面正文变成源码 | 单个 markdown 块过长，客户端截断 | 拆成多个 markdown 块或缩短 |
| 整卡「请升级客户端」 | 2.0 卡发给 v2 客户端 | 改 1.0/div+plain_text，或升级客户端 |

## 五、时有时无不是渲染问题：先数卡片生产方

**判据：单张卡片渲染错 → 查渲染层；卡片"有时有一时没有" → 查有几个生产者。**

同一台机器上能同时存在多套发卡通路，它们互相覆盖而不是排队：

| 生产者 | 开关在哪 | 冲突表现 |
| :--- | :--- | :--- |
| 宿主原生 `card_replies` | `platforms.<plat>.card_replies` | 与插件抢同一个 message_id |
| 插件进度卡（如 task-progress） | `plugins.entries.<name>.settings.enabled` + `plugins.enabled` | 每个工具边界插一条新卡 |
| 第三方流式卡集成（自带 sidecar 常驻服务） | 独立 systemd 单元 + 自己的 yaml | 与被禁用的原生通路争夺渲染权 |
| `exec_approval_text` 之类旁路 | `platforms.<plat>.exec_approval_text` | 审批/交互卡走另一条路径 |

"偶发"有两种成因，先分清再动手：

- **多生产者轮流抢**：某次重启/改配置让其中一层重新起来或落下去。
- **单一生产者进程活着、功能静默失效**：`systemctl is-active` 是 active、心跳正常、
  日志里连一句报错都没有，但发出去的内容是空的。这一种最容易被误判成"客户端不兼容"，
  因为它同时满足"服务在线"和"消息丢失"两个看起来互斥的观测。

**用户的观测时间线优先于你从日志时间戳推断出来的机制。** 用户说"丢消息的时候那个服务一直在线"，
就不要拿一个"重启后短暂失效的窗口"去解释他实际看到的时间点——那个窗口覆盖不到他说的时刻，
理论就废了，弃掉重来，不要为它找补。

排查顺序（先枚举，再动手）：

1. **读仓库自己的集成文档**：`integrations/<name>/README.md`、`integrations/<name>/lock.json`、
   `docs/DEPLOY.md`。这类集成通常有 pin 的上游版本、验收门和回滚快照，
   文档里往往已经写明"不得与另一个卡片生产者并存"。**不要靠猜某条卡片是谁发的**——
   grep 不到字样就先承认未知，别急着禁用某个插件。
2. **列服务**：`systemctl --user list-units '<相关前缀>*' --all`，看有没有自带 sidecar 在跑。
3. **列开关**：把上表四个键的当前值一次打出来（`/usr/bin/python3 -c "import yaml..."`，
   WSL 里 `python3` 常缺 PyYAML）。
4. **对账**：文档说应该是 false 却说 true，就是"偶发"的可疑层——先修这一处，别再往下猜。
5. **读生产者的自报计数**：第三方集成几乎都带 `status` / `doctor` 子命令，里面的
   `events_received` 对 `send_attempts`、`send_successes` 对 `send_failures`、
   `update_attempts` 对 `update_successes` 能一句话分开"没发"和"发了但是空的"，
   比翻日志快一个数量级。字段含义与探测顺序见 `references/streaming-card-sidecar.md`。

禁用任何一层之前先确认它是不是当前唯一的那层；基于猜测的禁用会变成新的故障源。
真要试禁用，**同一句命令里就把改前值回显并记下**（`本次 X=false ← 原值 true，回滚：...`），
否则下一轮你已经不记得改了什么，也没法向用户证明“不是你关的”。

**一个回合只能有一个生产者。** 这是业界共识，不是风格问题：宿主原生终稿与卡片 sidecar 同时写同一轮回复，
两边都不知道对方发了什么，结果就是一条被覆盖或互相挤掉。判据就在日志里：
`Normal final-send NOT suppressed ... content_delivered=False` 紧跟 `Sending response (N chars)`，
说明这一轮是**宿主自己发的**，sidecar 没有接手——所以这一条消失的回复**不能**归咎 sidecar
（它的 `send_attempts` 也不会为这一轮增长）。先读这句再决定查哪一层，
不要因为 sidecar 计数“零失败”就替它开脱，也不要因为它在跑就定它的罪。
三种主流 IM 的流式实现方式、「选卡片还是纯文本」的取舍，以及**换库选型判据**（官方 SDK / 轻量 CardKit 封装 / Hermes 专用),见 `references/im-streaming-modes.md`。

**零失败不等于送达。** `send_failures: 0` 且 `successes == attempts`，只证明卡片对象被创建成功，
不证明里面有你写的内容。看到"全部成功"而用户说没收到，下一步查**载荷内容**（首帧是否为空、
更新帧是否携带正文），不要回头再怀疑投递链路——那条已经用计数排除了。

**同理：计数也不能证明故障不存在。** 计数全绿只能把怀疑范围从"投递失败"挪到"内容为空"，
它本身不是"系统正常"的证据。别用一串 0 失败去反驳用户的实际观测——用户说没收到，
就是没收到，去拉那一轮的分界证据（见上文排查纪律）。

## 六、修第三方集成的缺陷：先数安装位

这类集成的代码通常装在**两处**，只换一处等于没修：

1. sidecar 自己的 venv（配置里的 `service.python_executable`）——跑 HTTP 服务，负责发卡；
2. **宿主网关的环境 venv**——`<hermes_root>/gateway/run_turn.py` 里有 `from <pkg>.hook_runtime import should_suppress_native_response`
   这类**进程内导入**，宿主自己也会加载同一个包。

判据：把两边的同名模块哈希对一下，不同就是两套代码。

```bash
python -c "import hashlib,pathlib;print(hashlib.sha256(pathlib.Path('<side-pkg>/hook_runtime.py').read_bytes()).hexdigest())"
# 对宿主 venv 的同一路径再算一次
```

- **契约变更必须两端同时生效**：sidecar 新增了回执字段，旧宿主模块不认识这个字段，会退回旧行为
  （例如仍然补发原生文本）。先确认补丁集里是否**同时**含宿主侧模块（`hook_runtime`），
  再谈"修好了"。
- **磁盘换了不等于内存换了**：宿主启动时 import 过的模块缓存在 `sys.modules`，改文件不会影响已在跑的进程，
  必须重启宿主。重启后核对两件事：PID 变了、两边模块哈希一致。
- **宿主不能在自身进程内重启**：工具守卫会直接拦掉（SIGTERM 会连带杀死执行中的命令），
  把重启写进命令行的间接写法（`systemd-run --on-active ... restart <网关>`）一样被拦。
  默认做法：把 `hermes gateway restart` 交给用户在**外部 shell** 执行，并附重启后的验证清单。
- **用户明确要求“你自己重启”时，用 systemd 用户定时器**：systemd 拥有该单元、不是网关的子进程，
  SIGTERM 杀不到它。把重启写进 `~/.config/systemd/user/<name>.service` 的 `ExecStart
  =/usr/bin/systemctl --user restart <网关单元>`，配一个 `OnActiveSec=<秒>` 的 `<name>.timer`
  （`Unit=<name>.service`），`systemctl --user daemon-reload` 后 `systemctl --user start <name>.timer`。
  `OnActiveSec` 留 40–60 秒让当前回复先发出去；触发后核对 PID 变化与两侧模块哈希，
  再 `stop` 定时器并删掉两个单元文件——留在盘上就是第二个调度源。
- **产物校验只认报告里记录的哈希**：构建出的 wheel 解压后算目标文件 sha256，与评审报告记录的
  上一条比对，一致才能说"部署的是评审过的那份"；不一致就是构建源不对，别往下装。
- **补丁有依赖顺序**：在裸源码上 `git apply --check` 失败未必是补丁坏，常见的是后续补丁需要前置补丁
  先落地。按发布顺序逐个应用后再回验。
- **回归测试可能是 opt-in 的**：不设 `*_SOURCE_ROOT` 之类的环境变量时整套会全 `skipped`，
  `skipped` 不是 `pass`；先看它是否真的执行了，缺依赖就建专用 venv 再跑，不要用系统 python 硬跑。
- **基础验收 `ready` ≠ 可生产**：`--infrastructure-only` 只看安装/健康/兼容，不看交互。
  静态缺陷清单里仍列着旧版本缺陷是**门禁产物**（它比的是 pin 的上游版本），不是当前代码的事实；
  但也不能因此宣布“缺陷已消除”——真正的证据只有回归测试通过 + 用户端观测。
- **回滚快照要覆盖所有安装位**：sidecar 配置（`python_executable` 那行）、systemd 单元、
  **宿主 venv 的包目录**。只备份 sidecar 配置的回滚计划是不完整的。

完整构建/切流配方见 `references/card-sidecar-deploy.md`。

## 七、验收

- 发一条含 14 行表格 + 表格后说明的真实回复，肉眼确认：原生表格、**只出现一次**、说明是正文；
- 中转/兜底的纯文本链路不能出现竖线与 `#` 标题标记；
- 回归：把这条回复喂给卡片构造器，断言元素标签序列（mock 即可）。

**验收只认两样：用户端显示，或对方明确说看到了什么。** API 回执（`code: 0`）、读回 body、
日志无报错，三者都可能在卡片实际不可用时全部为绿——尤其 2.0 卡（读回恒为占位符）。
拿不准时，**发两张对照卡**（同样的正文，一张 1.0、一张 2.0，标题写清①②）让用户指哪张正常，
一次问清，别自己猜着改一轮又一轮。
