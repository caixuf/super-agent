# T-D 自动回合占比实测（手册第四节第 3 条的量化依据）· 测试报告

日期：2026-10-26
执行人：Agent（远端宿主 现场）
性质：**只读测量**。所有查询在 `state.db` 的 `/dev/shm` 副本上执行，生产库未被打开写事务，未重启任何服务。
上游依据：`2026-10-26_core-execution-guide.md` 第四节第 3 条「57/63 个自动回合的来源」

## 一、为什么先测再改

手册说「后台完成通知会再开一个 LLM 回合，这是 57/63 个自动回合的来源」。
这句话如果成立，G2 是头号优先级；如果不成立，先改投递侧就是白改。

G2b 要动的是生产网关（`admit_process_notice` / `_inject_watch_notification`），
一次改错就会让通知静默或放大。所以在动它之前，先拿生产库把这句话变成可核对的数字。

## 二、测量方法与结果（原样）

数据源：生产 profile 的 `state.db`（160 MB，路径含业务 profile 名，本仓不写字面量）→ `/dev/shm` 副本 → `sqlite3` 只读查询。

### 1. 受理总量与自动占比

```
automation      : 179
human / other   : 643
total           : 822
automation 占比 : 21.8%
```

`automation` 的判据是 `principal_id LIKE 'automation:%'`——这是 `admit_automation`
写入的唯一 principal 形态，人发消息不会命中。

### 2. 179 条自动受理的形态

| 形态 | 条数 | 含义 |
| :--- | ---: | :--- |
| `native_text_v1.automation`（无 heartbeat/kind 字段） | 122 | 进程/后台完成类通知，走的是「合成消息 → 完整回合」 |
| `local_automation_v1` | 57 | LOCAL 平台的自动化回合 |

### 3. 放大集中在哪

| 会话 | 自动受理 | 人工受理 |
| :--- | ---: | ---: |
| `20261017_015106_ac2188a2` | 122 | 214 |
| `local-34211173…518` | 50 | **1** |
| `local-a15f278e…280` | 4 | 1 |
| `local-2be946fe…416` | 3 | 1 |

第二行是手册所说「通知放大」的落点：**一个只有 1 条人工消息的会话，产生了 50 个自动回合**。
这不是模型啰嗦，是完成通知每来一次就开一回合，回合内的查询又触发新的完成通知。

### 4. 自动受理携带的身份

抽样 `request_id`：

```
["completion","proc_bdc6275c356b",1792999408.0942295]
```

形如 `[类型, proc_<id>, 时间戳]`——即**进程完成事件**，而不是 `durable_submit` 的
32 位任务号。这与第一节的结论一致：当前放大的是「进程/后台任务完成通知」，
durable 队列的完成回执反而从来没被投递过（见 T-C 报告）。

### 5. 附带确认：路由信息其实已经持久化了

`native_text_v1` 的信封里同时存了：

```
route                    : <session_key>
source.chat_id           : <会话 id>
source.chat_type         : dm / group / …
source.thread_id         : <话题 id 或 null>
source.user_id           : <用户>
provenance.platform      : <连接器>
```

这一点很重要：**完整回填地址在受理时就已经落库**，缺的不是数据，是把这份地址交给
工具面的通道（宿主 patch）。所以 G3 的 agentcore 侧补了 `(profile, session)` 之后，
`session_key` / `chat_id` / `thread_id` 都能沿 `session_id` 从这条受理记录还原。

## 三、结论（对着手册那句话）

- 「后台完成通知会再开一个完整 LLM 回合」：**成立**，122 条 native automation 就是它。
- 「占比 21.8% 的受理是自动回合」：**本次测量**。手册的 57/63 是某个历史窗口内的观察，
  本次没有复现那个窗口（自动受理按 `seq` 无时间列，无法按时间切片复算），
  因此**不能**说 57/63 被证实或推翻，只能说同现象在整体上量化为 21.8%，
  且放大高度集中在单会话。
- 「放大是通知自激」：**有证据**。`local-…518` 会话 1 条人工 → 50 个自动回合。

## 四、未验 / 边界

1. **没有时间维度**：`session_admissions` 无 `created_at`，只能按 `seq` 顺序近似，
   无法给出「每小时自动回合数」这类时间序列。要做需要加列，属于 schema 改动，未做。
2. **122 / 57 的形态分类是启发式的**：判据是 payload key 的有无。`kind` 字段缺失时
   按 `heartbeat` 键推断，可能有个别误分类。
3. **没有归因到具体产生者**：进程 id（`proc_*`）能追到哪个后台进程，但没去核对
   `longtask_guard` 是否把某些前台命令也后台化了。手册记录过这类副作用。
4. **没有做因果实验**：本报告只说明"自动回合很多且集中在单会话"，
   不能证明"关掉通知后自动回合会降到多少"。那需要改代码 + 观测，属于 G2b。

## 五、这份测量影响什么

- G2b 值得做：21.8% 的受理、单会话 50:1 的自动/人工比，代价是真实算力与上下文污染。
- 但 G2b 的收益上限不是 21.8%：真正的目标是「完成通知不再消耗完整回合」，
  而要证明收益，需要 G2b 之后再用同一套查询复测一次（同一副本、同一 SQL）。
  本报告即是那次复测的**基线**。
