## T8：能力漂移告警

### 现状与接入点

- 现场 profile 的 `scripts/capability_guard.py` 已复用宿主巡检器的 `inspect_capability_baseline()`，检测和修复逻辑应继续只有这一份权威实现。
- 守卫在无漂移时静默；同一消息签名去重；恢复健康清签名，使下一次同类漂移可重新告警。
- 未配置通知目标时返回 3，发送失败返回 4，且不记成功签名。这一点已有明确失败语义。
- 当前去重状态采用普通 JSON 写入，不是事务 outbox。发送成功后、记状态前崩溃仍可能重复发送；并发运行也可能重复。

### 应补的机制

1. 在既有巡检结果与发送器之间接持久 outbox，不新增第二套能力基线表。
2. 每个 profile/scope 保存漂移 episode；同 episode 不重复建消息，健康观测结束 episode。
3. 单事务写 episode 与 outbox；消息携带稳定 event_id。
4. 发送器以租约认领，成功确认后标记 sent；超时租约可重领，旧 worker 不能确认新租约。
5. 记录检测值、期望值、是否已落盘修复和运行时是否已加载，避免把“写入配置”称成“已生效”。
6. 渠道若不支持幂等键，必须承认发送确认不明窗口，不能承诺绝对只发一次。

验收：正常周期零消息；压低白名单能力值后恢复并发一条告警；连续两轮不刷屏；恢复后再次压低可再告警；发送失败或 worker 崩溃后事件不丢；并发发送器只认领一个租约。真实通知需用户指定目标并实测，本轮未发。

## T9：联网自学习

### 机制选择

可参考研究 agent 的检索、引用与综合流程，但不照搬无限自主循环。定时器只负责提交任务，执行走持久 worker；独立证据审查后才允许正式入库。调研候选入口：GPT-Researcher、STORM、LangChain research agent；本轮未重新联网核验这些项目的当前接口，实施前需固定版本与官方来源。

### 建议的数据路径

检索任务 → 有界抓取 → 原始来源快照/哈希 → 原子候选事实 → 独立审查 → 正式记忆写入 → 召回探针 → 回执。

候选字段至少包括：candidate_id、statement、literal_quote、source_url、source_hash、retrieved_at、domain/scope、review_status、reviewer、reviewed_at。URL 与原文均按不可信数据处理，不能变成工具指令。

### 接入点与完成步骤

1. 由 T2 worker 领取受预算控制的检索任务；调度器不持有浏览器与模型执行上下文。
2. 抓取结果保留时间与来源；候选引文必须能在来源快照中逐字定位，失败即拒绝。
3. 将候选与正式记忆分库存放，候选不会参与默认召回；来源缺失、冲突未解、证据不足不能自动 approve。
4. 审查通过后调用既有 `agentcore.memory.memory_store.write_fact()`；使用稳定 source/candidate identity 避免重复灌入。
5. 写入后等待 `flush_background()` 完成，以新会话的真实召回判据核对命中与 scope 隔离。
6. 定时器仅在新知识通过、失败或需要人处理时回执；来源没有变化时静默。

验收：测试来源包含一条明确事实时形成可追溯候选；伪造引文拒绝；来源重复不重复入库；待审候选不进入正式召回；审查通过后新会话不主动查库也能命中；跨 scope 不泄漏。检索、定时、审查与新会话链路均须实测后才能称完成。

## 实施顺序

先完成 T2 持久 worker → T8 durable outbox 与隔离故障验证 → T9 候选知识及审查链 → 真实渠道与自动召回验收。T6 可先核对固定提交自检，发布推送依凭据状态推进。
