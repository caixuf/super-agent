# 唤醒风暴：同一件事被反复回一遍

## 技能定位

回答「为什么机器人把同一件事说了好几遍」——定位是**投递层重复**还是**多个回合各自作答**，
并把修复落在正确的层。**不适用于**：单纯措辞啰嗦、模型自己啰嗦（那属于表达，不是投递）。

> 核心判据：**先数"回合数"，再数"消息数"。**
> 回合数 == 消息数 → 每回合各答一次（唤醒风暴）；回合数 < 消息数 → 投递层真重复。

## 一、先分清两种"重复"

| 现象 | 判据 | 修在哪 |
| :--- | :--- | :--- |
| 投递层重复 | 同一次回合产出了多条相同消息 | 适配器/去重开关 |
| **唤醒风暴** | 日志里出现多条 inbound，各起一个新回合 | **插件越权 + 作答纪律** |

日志判据（`gateway.log`）：

```bash
grep -cE 'Watch pattern notification|inbound message.*Background' <profile>/logs/gateway.log
```

同一条待办如果注入条数 ≈ 任务条数，就是唤醒风暴，不是投递重复。

## 二、根因通常在插件越权

后台化插件的职责是**别占住当前回合**，不是**决定何时叫醒 agent**。
当它无条件写死 `notify_on_complete=True` 时：

- 宿主的 `display.background_process_notifications` **管不住它**——那一档只决定"要不要给聊天补一条收条"，
  而 `notify_on_complete` 决定的是"要不要开新回合"，两者是不同通道；
- 每一次后台进程退出 = 一次新回合 = 一次重新作答 = 一条重复消息。

**修法**：唤醒策略下沉到 profile 配置，插件默认不改全局语义。

```yaml
plugins:
  entries:
    <plugin-name>:
      settings:
        notify_on_complete: false   # 只要后台，不要每次完成都开新回合
```

同时**保留可观测性**：后台进程照常登记进活体账本，需要时用任务状态工具查，不要为了静音而丢证据。

## 三、判定要"宁窄勿宽"

误伤一个 0.2 秒的查询，比漏掉一个真长任务更糟。但反过来，
把 20 秒的等待当长任务转后台也是净亏——**省 20 秒，代价是多一次唤醒**。

判据要带**量纲**：`sleep 20` 不转、`sleep 120` 转；判不了的（如变量拼接）一律放行。

## 四、作答纪律：同批回执只回一条

即使机制修好了，纪律仍要守住：

- 同一批任务的多条完成回执 → **只在最后一条回执时回一条汇总**；
- 中间那些回执**不回话**（不要每条都写"已收到"）；
- 结论没变化时，一句话带过；**不要重复报告已经交付过的产物和链接**。

## 五、验收（可执行）

改完后跑这三行，看数字对比：

```bash
# 1) 后台化次数（应当 > 0，说明转后台没坏）
grep -c '转后台' <profile>/logs/agent.log
# 2) 唤醒次数（关键指标：应当显著下降或为 0）
grep -cE 'Watch pattern notification|inbound message.*Background' <profile>/logs/gateway.log
# 3) 插件单测（判定逻辑必须有负例，负例多于正例）
bash <repo>/tests/run_<plugin>_tests.sh
```

判据：**转后台次数不变，唤醒次数归零**——说明修的是唤醒，不是把长任务塞回前台。

## 六、反模式

| 反模式 | 真实代价 |
| :--- | :--- |
| 把"多说了几遍"当成投递层 bug 去查去重 | 查错层，真正原因在唤醒策略 |
| 靠"我下次注意"解决 | 纪律会漏，必须落到配置或代码 |
| 为静音而丢掉账本/证据 | 事后查不到任务状态，可观测性归零 |
| 把判断写成纯关键词匹配（`sleep ` 一律命中） | 20 秒等待也转后台，唤醒数不降 |
| 改了插件却不重载 | 代码改了，跑的还是旧模块，改动"看起来没生效" |

## 七、重载（改完必做）

插件是**进程内模块**：改文件不等于生效。按部署方式选一种，重载后再验：

- 优先走网关控制通道的热重载（不重启进程）；
- 其次重启网关服务；
- 两者都不可用时，说明"改动已落盘但未生效"，不要报"修好了"。
