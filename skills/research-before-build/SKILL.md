# 先调研再动手：把「重复造轮子」挡在动手之前

## 技能定位

回答「接到一个新需求，动手前必须查什么、查到什么程度算够」。**不适用于**：一句话可答的问题、
用户已给定实现路径且只差落地、排查已知故障（那走调试类技能）。

> 核心判据：**能指出「这次用了哪里的东西、为什么不用现成的」才算调研完成。**

## 一、动手前的四类调研（按成本从低到高）

| 顺序 | 查什么 | 怎么查 | 停止条件 |
| :--- | :--- | :--- | :--- |
| 1 | **已装能力** | 列出工具面与已启用插件（`tools list` 类命令或技能目录），确认是否已经有这个能力 | 已有现成工具/插件 → 直接用，不写代码 |
| 2 | **本机既有实现** | 搜本机代码与脚本（按功能关键词，不按文件名猜），看是否有同义实现、半成品、历史分支 | 找到可复用的模块/脚本 → 改造它，不新建 |
| 3 | **仓库与依赖生态** | 看依赖清单与 lock、vendor 目录、已引入的库是否已覆盖（如 `httpx`、`pydantic`、平台 SDK） | 依赖已覆盖 → 用它，不新增依赖 |
| 4 | **公开方案与上游文档** | 官方文档先于博客；看官方是否有对应 API/配置项；看上游仓库是否已有同类实现或 patch | 官方已有入口 → 走官方，不自己拼 |

每一类只做一次、写明结论（「查了 X，结论 Y」），**不要为了显得认真而反复搜**。

## 二、判断「要不要自己写」的三条硬规则

1. **官方有入口就不自己拼协议**：例如平台已提供导入/转换接口，就不要手写它的编码或私有块结构。
2. **本机已有实现先改造**：同一台机器上两份同义实现，是最常见的重复造轮子；改造前先确认调用方，别造第三个。
3. **新增依赖要给出理由**：能用一个标准库能力或已有依赖完成的，不引入新包；引入时写清版本与 pin 方式。

## 三、产出格式（写进任务说明，不写成长篇）

```text
调研结论：
- 已装能力：<有/无> —— <用什么>
- 本机实现：<路径> —— 复用/改造/为何不适用
- 依赖生态：<已覆盖/需新增> —— <理由>
- 上游/官方：<入口链接或命令> —— 采信理由
决定：<做>（复用 X；新增 Y，因为 Z）
```

**空着的行也要写「无」**，不要留白——留白等于没查。

## 四、反模式

| 反模式 | 真实代价 |
| :--- | :--- |
| 直接开工，事后才发现官方有现成接口 | 返工 + 与官方行为不一致 |
| 只搜关键词不看已有模块 | 同一仓库第二份实现，之后两份一起漂移 |
| 为了「可控」引入一个大依赖替换标准能力 | 体积、许可、升级成本 |
| 调研写成流水账，没有「为什么不选另一个」 | 下次还得重查 |

## 五、验收

- 任务说明里有上面四行结论 + 一句决定；
- 若选择自己写，必须写出「官方/现成的为什么不够用」，否则默认应复用；
- 涉及平台 API 时，引用的是官方文档链接或本机 `--help` 输出，不是记忆里的说法。
