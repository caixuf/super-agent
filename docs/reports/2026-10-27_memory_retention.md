# 记忆候选有上限，归档后也能找回

本次处理自动压缩留下的候选，补齐 T7 的一部分。它不压缩事实库，也不宣布整套记忆治理完成。

## 默认规则

在线待核对候选最多 128 份，文件内容合计最多 32 MiB。相同原文与候选重复提交只占一份；新增报告版本仍计入字节预算。写入共用跨进程文件锁，两路写入不能同时抢到最后一个名额。满额时拒绝新候选，正式记忆和已有候选保持不变。

归档区最多 512 份、128 MiB，不按年龄自动删除。归档先复制 before.md、candidate.md 和所有报告，生成逐文件长度及 SHA-256 清单，落盘后重新核验，最后才移出在线队列。中途失败仍保留在线原件；重试能处理上次清理到一半的状态。链接、目录穿越、不完整候选和来源哈希不一致都拒绝处理。

恢复先核验归档，再检查在线容量和冲突，逐字恢复候选。**恢复候选不等于应用候选**，不会写入正式 MEMORY.md 或事实数据库。归档本身继续保留，供再次恢复。

## 操作入口

在仓目录运行，`<queue>` 是 profile 对应的私有保全目录，`<id>` 是工具返回的 proposal_id：

```sh
python3 -m agentcore.memory.proposal_archive --root <queue> status
python3 -m agentcore.memory.proposal_archive --root <queue> archive <id>
python3 -m agentcore.memory.proposal_archive --root <queue> restore <id>
```

容量拒绝时先检查候选，不得通过删原文、删旧版本、修改审阅文件来绕过。可将已经核对完的候选归档；归档也满时停止新增并安排经验证的外部存储。没有自动清空历史的兜底路径。

## 范围与验证

专项覆盖容量拒绝、重复提交、并发最后一个名额、归档恢复、满额恢复、篡改、链接与来源不一致。实际宿主继续验证 MemoryStore 仍按原有规则拦截有损改写。

本轮专项 19 passed，完整通用回归 798 passed、9 skipped，Shell 和安装器 dry-run 通过。真实宿主还填满了默认 128 个名额，确认工具明确返回 conservation_capacity_exceeded、staged=false，原文和进程内条目均未改变，不会谎报“候选已保存”。

现场使用 13,798 字符的正式记忆副本，走完满额拒绝、归档释放名额、满额恢复拒绝、逐字恢复与重复归档。正式源文件哈希未变。另有中途复制和中途移出在线队列的恢复测试；这与在线事实库压缩是两件事，不能拿前者代替后者的验收。

现场备份脚本及定时作业的配置属于业务仓：旧快照先固定保留，容量满则停止新增，不能因为有了一个新快照就删除未核对的旧版。整库快照保留、事实压缩与完整旧事实清单仍是独立待办。
