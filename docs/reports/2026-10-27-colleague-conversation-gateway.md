# 同事对话怎样接入现有机器人

这个说明记录的是当前代码的接线方案，不代表功能已经上线。

## 用户看到什么

在现有机器人账号里转交结果时，应明确告诉用户“由谁转交、来自哪位同事”，例如：

> 主 Bot 转交｜开发同事小林｜任务 123
>
> 我检查了相关代码，发现……

如果只是主 Bot 自己归纳了同事的材料，要标明“主 Bot 根据开发同事的结果整理”；不能标成同事亲自说的话。平台上的发送账号仍是主 Bot。只有平台实际配置并认证了独立机器人账号时，才能显示成另一个平台发送账号。

姓名和岗位是展示信息，任务与同事的绑定由宿主保存。不能从模型生成的正文、签名或岗位名称推断出具体同事。拿不到可信的成员绑定时，应该显示岗位或“成员身份未确认”，不要编造姓名。同名成员也需要内部稳定身份区分；显示名称变更后，旧消息应保留当时的身份快照。

## 现有代码能做什么

`plugins/durable_dispatch` 提交任务时保存宿主绑定的 profile、会话和路由；`runtime/hermes_completion_transport.py` 使用宿主的路由解析与平台适配器，核对目标后直接发送文本和文件。它发送的是独立消息，不会启动一次新的模型对话。只有拿到平台消息 ID 才确认交付；发送结果不明时不会盲目重发。

这条旧回填路径目前按任务渲染，没有读取同事身份。新的 `colleague_workflow_delivery` 则只有注入式接口，还没有接上真实平台传输。工作流最终记录只保存岗位和子任务信息，尚未持久绑定具体成员；两条路径不能同时向用户发送同一个结果，否则可能重复。

现有回填会核对提交时记录的聊天路由，而不是使用当前打开的聊天。但同一聊天在用户开启新会话后可能仍复用路由，因此不能把路由匹配当成严格命中原历史会话。缺少路由时应保留结果待查，不能猜测收件人。

署名只解决“看见谁在说话”。如果用户希望接着说“让小林继续”或引用小林的消息追问，还需要单独的入站路由：由宿主把用户当前聊天、引用消息或明确指定的成员，与有权访问的团队成员和对应会话关联；不能让模型编造路由或把另一位用户的对话带进去。现有登记和回填还没有实现这条双向路由，也没有让新同事获得独立的持续对话。

## 建议的接线和验收

1. 宿主接单时将稳定成员 ID、实例代次、任务 ID 和发言人显示快照一起持久化；每次展示前核对该绑定与任务归属。身份绑定必须来自宿主，不能由模型自报。
2. 给工作流选定唯一的最终消息发送方；内部子任务只在队列内确认，不向用户重复回填。真实平台收到匹配的送达回执后才能确认；结果不明时保留待核对状态。
3. 先用主 Bot 账号发送带清楚署名的普通消息，并通过受控的同一受众路由提交；独立机器人账号、单卡持续更新和附件是需要各自接线与验收的能力，不能因纯文本签名通过就视为完成。
4. 在隔离测试环境验证：两名成员同时回复、同名成员、成员更名或停用后旧结果回传、两个聊天并发、同一聊天开始新会话、引用消息追问、发送超时和重启。逐项检查消息只送给原受众、说话人和追问目标不串、主 Bot 转述没有冒充原话、成功结果不重复。
5. 最后由用户手动在真实聊天发送测试消息，人工检查显示效果、交接和回传。真实平台、卡片和不同网络状况不能由模拟适配器的测试代替。

当前没有将这套显示方式或新的最终投递器启用到现有机器人。
