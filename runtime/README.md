# runtime/ — 运行时配置基线（骨架与纪律）

## 一句话

**这里只放与业务无关的运行时骨架与纪律。业务键及其取值由业务叠加层提供** —— 哪些键是业务的、
它们的真实取值，属于业务内容，写在业务仓的部署清单里，不进本仓。

## 文件

| 文件 | 用途 | 落地位置 |
| :--- | :--- | :--- |
| `hermes-agent.service` | 网关常驻单元的**骨架**（user 级） | 由 `hermes gateway install` 生成真实单元；本文件只作参考 |

本目录**不提供** `config.yaml` / `env` 的整份模板：那些键名与取值随宿主环境漂移，
写死在仓里就会变成「溜进通用仓的业务默认值」。模板由部署方按现场环境自建。

## 三条纪律

1. **不要整文件覆盖现场 `config.yaml`。** 现场配置可能内联了凭据；整文件覆盖会静默冲掉它们。
   做法是**逐键补齐**（比对现场缺哪些键），而不是照搬别处的键值。
2. **仓里不放任何密钥。** 密钥一律走 `env_file`（600），键名清单由部署方自己维护。
3. **数值是【现场实测值】，不是默认值。** 窗口探测（`context_length`）、压缩阈值、并发预算、
   `agent.max_turns` 这些随环境与实测漂移，**照搬前必须在新机器重测**。

## 能力基线（不可静默下调）

下面这些不是调参旋钮，是**低于某值则整类工作变得不可能**的底线。它们必须由巡检作业
**检测并回写**（`config.yaml` → 临时文件 → 原子 rename），而不是靠人记得检查：

- `agent.max_turns` —— 轮次上限会把长链条诊断（取证 → 定位 → 改 → 测 → 验收）从中间截断，
  半途而废的重来代价远大于省下的 token；
- `delegation.max_iterations` / `max_concurrent_children` / `max_spawn_depth` —— 同一逻辑，低一层；
- 用户明确设定过的开关（关掉的审批门禁、要的展示行为）—— 静默回退必须被检出。

**注意区分**：检测并回写的是**配置值**；`SOUL` / `AGENTS.md` 这类指令文件的写入另有门禁，
**必须保持人工决定，不要接到自动修复里**。

## 通用键 vs 业务键怎么划

判据：「**换一个行业 / 换一台机器还要不要它？**」

- 要 → 通用键（可进本仓骨架）；值若是现场实测的，照搬前重测；
- 不要（指向某个平台的 MCP 服务、某个行业的技能目录、某个厂商的 provider 别名）
  → 业务键，由业务叠加层在部署时补齐。

占位符约定（与 `identity/SOUL.generic.md` 同一套）：`<business-mcp-server>`、
`<business-provider>`、`<business-skills-dir>`、`<business-profile>`、`<BUSINESS_*>`、
`{{BUSINESS_OVERLAY}}`。
