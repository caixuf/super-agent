# MIGRATION.md — 把「靠人工手配的智能体」收编成可一键复制的仓

本仓（`agentcore`）的定位：**与业务零耦合的「智能体本体」技术仓**。
目标是让迁移变成「clone + 跑 `install/install.sh`」。业务内容**不进本仓**，
由**业务叠加层**（业务仓 / 业务知识库 / 业务工具 / 业务仓库的部署清单）在部署时提供。

## 0. 路径词汇（本文用占位符代替真实名字）

| 占位符 | 含义 |
| :--- | :--- |
| `<business-repo>` | 业务仓根（本机部署位，只读引用） |
| `<business-skills-repo>` | 业务技能源仓（独立 git 仓） |
| `<business-mcp-server-dir>` | 业务 MCP 服务所在目录 |
| `<business-profile>` | 部署画像名（Hermes profile） |
| `<mcp-env-name>` | 业务 MCP 子进程环境文件名 |
| `$HERMES_HOME` | 宿主 Hermes home（带画像时是 `$HERMES_HOME/profiles/<business-profile>`） |
| `<host-identity>` | 本机身份（主机名、角色、部署位） |

> 「真实路径 → 占位符」的映射属于业务内容，由业务叠加层的部署清单给出。
> 同理，本表**不写**任何业务键名、业务工具名、业务画像名。

## 1. 八层迁移清单

每层回答三件事：**现居何处 → 迁移动作 → 验收检查**。

### ① 身份与纪律

| | |
| :--- | :--- |
| **现居何处** | 业务身份全文在 `<business-repo>` 的身份文件里；**生效副本在 git 之外**：`$HERMES_HOME/SOUL.md`（带画像时 `$HERMES_HOME/profiles/<business-profile>/SOUL.md`）；另有一份 profile 级常驻契约 `$HERMES_HOME/AGENTS.md`（也在 git 之外）；派工契约在 `<business-repo>` 的 agents 目录 |
| **迁移动作** | ① 把**通用机制与纪律**抽成 `identity/SOUL.generic.md`（工具分流分层 / 系统内部自足 / 结论先行 / 长任务后台化与并发分级 / 记忆先查再动手 / 交付与验收纪律 / 写保护与审批通道），业务处一律占位符；② 派工契约（reader / triage / author / runner / triager / closure）通用化到 `identity/agents/`；③ 业务身份全文**留在业务仓**，本仓不留副本；④ 生效文件 = 骨架 + 叠加层，由业务层用 `--compose-soul` 合成 |
| **验收检查** | ① 本仓门禁绿（骨架零业务词）；② `bash install/install.sh --dry-run` 打印的合成计划指向正确目标；③ 合成后 `$HERMES_HOME/SOUL.md` 里 `{{BUSINESS_OVERLAY}}` 已被替换（`grep -c` 为 0）；④ **漂移检测**（只读）：对「本仓骨架 + 叠加层」与「生效文件」做 whitespace 归一化后逐字节比对 —— 不许建自动同步（会绕开指令文件写入门禁） |

### ② 技能库

| | |
| :--- | :--- |
| **现居何处** | 源仓 `<business-skills-repo>`（独立 git 仓，有远端）；**安装副本在 git 之外**：`$HERMES_HOME/skills/`；另有若干第三方工具各自的技能目录（`~/.claude/skills`、`~/.cursor/skills`、`~/.agents/skills` 等），由源仓的安装脚本批量铺开 |
| **迁移动作** | ① 通用 + 示例技能进本仓 `skills/`（示例放 `skills/examples/`）；② 业务技能**默认不装**，靠文档化挂钩叠加：`INSTALL_BUSINESS_SKILLS=1` + `BUSINESS_SKILLS_SRC=<业务技能源目录>`；③ 其余第三方工具的目录不在本仓职责内（各装各的） |
| **验收检查** | ① 本仓 `skills/**/SKILL.md` 逐个过门禁；② 默认安装后 `<HERMES_HOME>/skills/` 只多出通用/示例技能；③ 带上挂钩环境变量后业务技能才落位，且逐个 `diff -rq` 与源一致 |

### ③ 工具面

| | |
| :--- | :--- |
| **现居何处** | `<business-repo>` 下的执行器适配器目录、业务 MCP 服务目录（工具实现 + 工具注册表 + 依赖清单）；**部署副本在 git 之外**（一个只保留解释器与依赖的副本目录，代码指回业务仓） |
| **迁移动作** | ① 通用的**外部执行器适配器** → `toolsets/pi_executor/`（隔离目录、事件流判定、进程树清理、结构化回执）；② 业务工具实现 / 工具注册表 / 业务 MCP 服务本体**留在业务仓**（工具名就是业务名词）；③ 与业务 MCP 同目录的伴生件（如协议翻译层）按「部署位是业务的」一并留业务侧，不在本仓留副本 |
| **验收检查** | ① 本仓 `toolsets/` 内零业务词；② 部署后 `python3 -m py_compile` 通过；③ 业务侧 MCP 仍从业务仓 `cwd` 起（不得指向本仓副本），确认没有出现「改的是仓库、跑的是旧拷贝」 |

### ④ 记忆引擎

| | |
| :--- | :--- |
| **现居何处** | 引擎本体已在本仓（`agentcore/memory/`）；**运行时数据在 git 之外**：宿主数据目录下的事实库 / 注册表 / 突触账本 / 轨迹库，以及业务侧另有一个「决策锚点」事实库 |
| **迁移动作** | ① 引擎保持业务无关：业务约定（领域取值、代际写法与前缀、默认身份、嵌入后端、向量维度、领域词表）全部由宿主经 `MemoryConfig` 注入；② 本仓默认配置不得内置任何企业的领域名 / 代际名 / 词表（已有专门测试）；③ **数据不进仓**（`.gitignore` 挡 `*.db`；随包分发的原生扩展例外） |
| **验收检查** | ① `python3 -m pytest tests -q` 全绿；② 默认 `MemoryConfig()` 的种子字段零业务词（`test_business_words_only_in_injected_config`）；③ 宿主注入后能跑通「写入 → 后台汇合 → 召回」闭环，并断言**真的召回**（写入返回 `ok` ≠ 功能可用）；④ **搬库必须连同嵌入后端**：同一个嵌入模型 + 同一个 `embed_dim`。换了模型/维度，向量空间就变了 —— 表现为**召回全空但服务看起来一切正常**（最容易误判成「库里没有」的静默故障）。迁移三件套：事实库 + 突触账本 + 同一嵌入后端 |

### ⑤ 运行时配置基线

| | |
| :--- | :--- |
| **现居何处** | 模板在 `<business-repo>`；**现场 `config.yaml` 在 git 之外**：`$HERMES_HOME/config.yaml` 或 `$HERMES_HOME/profiles/<business-profile>/config.yaml`（含内联的 provider / MCP 段与密钥），同目录还有一大堆历史 `.bak` |
| **迁移动作** | ① 通用键的**判定口径**与纪律进 `runtime/README.md`，**段级归属与并行会话语义进 `runtime/CONFIG_MAP.md`**（判据：换行业/换机器还要不要 + 部署位归谁）；② 是否随仓提供占位符化的 `config.yaml` / `env` 键名骨架，**由 runtime/README.md 的口径决定** —— 本仓当前的选择是**不提供整份模板**（键名与取值随宿主环境漂移，写死在仓里会变成「溜进通用仓的默认值」），模板由部署方按该口径自建；③ **能力基线**（轮次上限、派工并发/深度/迭代、用户明确设定过的开关）单列，由巡检作业检测并回写，不靠人记；④ 可一键落地的那部分由 `install.sh --apply-baseline` 写入（**地板只抬不降**，且不碰安全开关） |
| **验收检查** | ① 若随仓提供键名骨架，它必须能被 YAML 解析、且零业务词（占位符齐全）；② 对齐动作**逐键补齐**而不是整文件覆盖（覆盖会静默冲掉现场密钥）；③ 现场值（窗口 / 压缩阈值 / 并发预算）在新机器上**重测**而非照搬；④ `install/install.sh` 对「有/无键名骨架」两种形态都能跑通（不硬编码文件清单） |

### ⑥ 平台适配补丁

| | |
| :--- | :--- |
| **现居何处** | 补丁与重放脚本在 `<business-repo>`；**被改的目标在 git 之外**：宿主 Hermes 安装树里的适配器文件（`hermes update` 会覆盖它） |
| **迁移动作** | 补丁 + 幂等重放脚本进 `patches/`；`patches/README.md` 写明「`hermes update` 后必须重打」与回退法；在位判定改为**内容探针**（标记函数 + 两个开关字段）为主判据 |
| **验收检查** | ① `--check` 报在位（退出码 0）；② `--apply` 重复跑幂等（第二次直接跳过）；③ 改动安装树后**必须重启网关**才生效；④ 配置侧 `--config` 能读出两个开关的真实生效值（抓「写了配置但读不到」） |

### ⑦ 服务与守护

| | |
| :--- | :--- |
| **现居何处** | **全部在 git 之外**：user 级单元（`~/.config/systemd/user/`，由 `hermes gateway install` 生成，含 `hermes-gateway-<profile>.service`）、系统级单元（`/etc/systemd/system/` 下的翻译层与平台服务）、`loginctl enable-linger` 的驻留设置、以及 cron 作业记录（`$HERMES_HOME/profiles/<business-profile>/cron/jobs.json`） |
| **迁移动作** | ① `runtime/*.service` 只作**骨架**（判据与坑写在注释里：为什么必须 user 级有 DBUS/keyring、为什么不抢 CPU）；② `install.sh` **只打印**人工执行的启停命令，绝不自己启停服务；③ cron 的硬约束（只许巡检/告警，绝不新增触发重型任务的 job；不要因为「觉得更安全」关掉它而静音唯一告警通道）写进模板注释 |
| **验收检查** | ① `runtime/*.service` 零业务词且占位符齐全；② `install.sh --dry-run` 输出里出现 systemd 命令但**没有任何服务被启停**（跑完 `systemctl --user is-active` 与跑前一致）；③ 巡检 job 仍在，且其提示词里带能力基线自检项 |

### ⑧ 凭据与接入

| | |
| :--- | :--- |
| **现居何处** | **全部在 git 之外，且都不打包**：`$HERMES_HOME/.env`、`$HERMES_HOME/<mcp-env-name>.env`、`$HERMES_HOME/channels.env`（各 600）、OAuth 令牌文件、profile 目录下的 `.env` 与其历史备份、以及第三方工具自己的凭据文件 |
| **迁移动作** | ① 本仓**不随仓提供** env 模板（键名清单本身即业务内容）；只写判定口径（换行业/换机器还要不要），业务键名由叠加层给出；② 装器**不读不写任何凭据文件**；③ 密钥永远不 echo / 不 log / 不入库（仓内已有密钥门禁） |
| **验收检查** | ① `git ls-files` 里没有任何 `.env` / 令牌 / 数据库文件；② 门禁扫全仓时凭据文件不在射程内（被 `.gitignore` 挡）；③ 部署后人工建 600 权限文件，且 `install.sh --dry-run` 输出只提示路径不给值 |

## 2. 目前**只存在于 git 之外**、不打包就一定会漏的东西

按「漏了会怎样」排序：

| 资产 | 位置（git 之外） | 漏了会怎样 | 处理 |
| :--- | :--- | :--- | :--- |
| 现场 `config.yaml` | `$HERMES_HOME[/profiles/<p>]/config.yaml` | 模型路由、窗口、压缩阈值、派工预算、MCP 注册全丢，机器人「能起来但变弱」 | 通用键进模板；业务键由叠加层；现场值重测 |
| profile 级常驻契约 | `$HERMES_HOME/AGENTS.md` | 项目级纪律静默消失（有契约测试读仓库那份，**绿测试不代表规则上线**） | 纳入 ① 层的漂移检测口径 |
| 身份生效副本 | `$HERMES_HOME/SOUL.md` | 身份/纪律回退到默认，行为漂移 | 骨架进本仓；合成由叠加层做 |
| 技能安装副本 | `$HERMES_HOME/skills/` | 通用/示例技能缺失（业务技能另有源仓，可用挂钩补） | `install.sh` 装；业务走挂钩 |
| cron 作业定义 | `$HERMES_HOME/profiles/<p>/cron/jobs.json` | 巡检/告警静音，故障无人知 | 作业清单进业务叠加层的部署清单 |
| 系统 / 用户 systemd 单元 | `~/.config/systemd/user/`、`/etc/systemd/system/` | 服务根本不常驻（重启后即失联）；快照与 `install.sh` 也会缺该有的 systemd 单元 | 骨架进 `runtime/`；真单元由 `hermes gateway install` 生成 |
| `loginctl enable-linger` | systemd 用户会话设置 | SSH 退出后 user 服务被杀 —— 表现为「平时好好的，断了线就没了」 | 人工步骤写进 `install.sh` 输出 |
| 安装树里的本地补丁 | 宿主 Hermes 安装树的适配器文件 | 功能没了但不报错，只是回复退回纯文本（最难查的静默退化） | `patches/` + `--check` 探针；`update` 后重打 |
| 运行时记忆/事实库 | 宿主数据目录下的事实库、注册表、突触账本、轨迹库 | 「以前踩过的坑」全部失忆；召回变空但服务看起来正常 | **不打包数据**；靠宿主的持久化目录 + 备份策略 |
| 决策锚点事实库 | 业务侧独立库（同名文件 + 备份） | 用户明确定过的设计/门限没有可查之处 | 不打包；由业务侧管理 |
| 凭据 | `$HERMES_HOME/*.env`、令牌文件、第三方工具凭据 | 服务起不来或只有只读能力 | **永不打包**；只给键名清单 |
| 第三方工具的技能铺开 | 各工具自己的 skills 目录（若干处） | 换个工具就没有技能 | 各工具各自的安装脚本负责，不在本仓职责内 |

## 3. 本段**没做**的（明确留白，不是遗漏）

1. **业务叠加层的具体内容与本仓的分层落地**：业务身份全文、业务工具面、业务键清单、
   业务技能源目录都留在业务侧；本仓只提供骨架 + 占位符 + 挂钩。**哪一天把叠加层做成
   一个可版本化的独立产物**（而不是靠业务仓的散落文件），本段没有设计。
2. **业务键清单没有进本仓**：一份「哪些键是业务的、真实取值是什么」的清单本身就是业务内容，
   所以本仓只写了**判定口径**（换行业/换机器还要不要 + 部署位归谁），没有列具体键。
3. **两个「与业务 MCP 伴生」的通用机制件没有进本仓**（协议翻译层、
   把外部执行器包成工具面的胶水）：机制通用，但部署位、凭据与 import 关系都在业务侧。
   要收进来必须先设计「通用件与业务部署位的解耦」，本段没做。
4. **会话准入/SOUL 写保护相关的改动**：本段只**记录**门禁语义（写保护开关与审批档位不是一回事、
   人工通道怎么走），没有改任何准入或审批实现。
5. **`install.sh` 的真实模式没有执行**：本段只跑了 `--dry-run` 与 `bash -n`；真实部署
   （以及 `--compose-soul`）需要在一台干净的机器上验收，本段没有机器。
6. **能力基线的自动守护没有实现**：只写了规则与位置，没有写巡检回写逻辑。
7. **本仓的 CI**：门禁是 pytest 层的（两条射程），没有接到任何外部 CI 流水线。
8. **多 writer 协作时的写入纪律**：本仓可能同时被多个改造者编辑（本段就遇到了），
   建议在任何「收编」动作前先确认工作区归属（谁在改、改到哪），不要互相覆盖。
