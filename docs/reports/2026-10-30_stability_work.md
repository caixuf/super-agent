# 稳定性排查与修复记录

## 现场观察

10 月 30 日，业务机器人网关和记忆召回服务在观察时运行中，召回健康接口返回 ready。此前召回检查点仍绑定旧存储的文件身份，迁移到新存储后无法启动；核对新旧库在旧库末尾的日志锚点一致后，保留原检查点并调整文件身份，服务恢复就绪。该核对证明检查过的位置一致，不证明所有可能的迁移故障均已解决。

系统盘曾经出现严重 I/O 等待，五组孤儿全目录搜索停留数分钟至一小时以上。按用户清理当前任务的授权，核对进程所有者、父进程和命令后发送终止信号，五组搜索退出；未终止业务编译或模型服务。此后 I/O 压力有所下降但仍偏高。设备采样中系统盘接近满负荷、请求等待达几十毫秒；这不等于硬件损坏，仍需结合持续采样和磁盘健康信息判断。

历史回执仍需单独核实：21 条未确认，其中 18 条缺少路由，另外 3 条指向 API 会话。不能猜测收件人重发，不能把降低日志频率当成修复投递。

## 本机代码改动

- 记忆召回的网络接入和健康响应不再与数据库执行串在一起；内存数据库仍由创建它的线程独占。慢操作时健康返回 busy，请求队列和客户端数量有上限，排队过期的请求不会执行。
- 回执积压 warning 限频；每轮投递和持久健康观察不受该限频影响。
- 自动召回后台预取与前台读取同一查询时共享正在执行的一次召回，等待不超过配置的召回超时；单个 provider 同时进行的查询最多 8 个，达到上限时跳过并记录告警，避免故障时无限增加子进程。超时或过载仍可能没有记忆，不能当作真实召回成功。
- 涉及记忆、回执及宿主的定向测试通过；系统 Python 离线回归 1554 项通过、24 项跳过，真实渠道发送未运行。Hermes 宿主相关定向回归 80 项通过。
- 回归后发现工作区另有并行修改 `memory_store.py`；上述结果不保证覆盖该文件最新状态。保留并行修改，集成前需重新核对并针对最终版本验证。
- 随后在当前工作树用 Hermes 解释器运行相关记忆、回执和中立性测试：124 项通过。这个结果覆盖当时的文件状态，但仍不是整库测试或真实业务验收。
- 增加 provider 召回容量限制后，系统 Python 针对相同领域复测 125 项通过；不可将其与上次 124 项相加。
- 并发等待同一召回的多个调用者各自获得该次结果；补充并发测试后相关回归 126 项通过。
- 一次现场召回服务重启曾因磁盘等待长时间停留在退出阶段，随后启动并报告 ready、进度 4137；不代表长期稳定或已完成业务召回验收。
- 后续健康变成 pending，进度停在 4214。只读检查该位置后的一批变更时，涉及的活动事实中有一条缺少向量、103 条标注的向量模型为 `BAAI/bge-m3`；进程配置使用默认 `bge-m3`，当前视图要求模型标识完全相等。它们是追赶被阻塞的具体候选原因，但同名是否同一实际模型和向量质量未核验，不能直接改数据库或当成等价。
- 后续观测同一批受影响的事实数量继续变化，发现现场已有独立的 `reindex_embeddings` 进程在运行。该进程非本次启动；不并发启动重复重建、不停止它，先以进程和健康状态确认其结局。当前 pending 并不等于该重建必然成功。
- 后续一次观察中独立重建仍在运行，召回服务报告 ready、进度 4688；还不能据此认定重建完成或真实对话召回已验证。
- 再次观察时，该重建进程已不存在；服务报告 ready、进度 7494。日志曾记录一次实际召回命中，但其后诊断文件仍记录过 `TimeoutError`，所以不能把健康接口 ready 视作召回链路已经稳定，也不能仅凭进程消失判断重建成功。
- 本机健康输出只对白名单内的 pending 原因提供原因码；观察器识别 busy 为忙碌而非无效响应。相关回归 128 项通过，尚未部署。
- 本机自动召回将子进程失败、异常格式、超时和过载与正常空结果区分：前者向模型注入简短不可用提示，后者保持无注入。相关回归 129 项通过；尚未部署到业务服务。
- 补充显式 `ok: false` 的失败处理，防止带空结果的失败响应被误当成没有相关记忆；本机当前相关回归 131 项通过，另用 Hermes 解释器运行宿主绑定等测试 74 项通过，两组有重叠。
- 新增 `python -m agentcore.model_latency_report <agent.log>`，只汇总已结束模型调用的小时分布、输入规模和延迟，不输出消息正文或会话 ID；它不统计仍在运行或失败且没有完成日志的请求。使用日志本身的本地时区，读取范围默认限于文件尾部 8 MiB。
- 通用任务状态查询只清扫当前会话的任务，不再为一次查询扫描并改写其他会话的任务；无 owner 参数的运维清扫保持原行为，更新时再次核对 owner。相关本机测试 103 项通过，Hermes 宿主相关测试 24 项通过（两组有交集）。尚未部署，此优化不能证明业务进度接口已经提速。
- 业务适配的现场配置将普通 MCP 请求超时设为 3600 秒，单次进度快照也继承该设置。本机业务仓库已将该快照的 HTTP 阶段等待上限改为不超过 5 秒，其他接口保持原值；相关测试 55 项通过，1 项因既有模型模板断言不一致而单独排除。现场源文件已在核对与备份后更新，但常驻 MCP 进程启动早于更新，尚未重建，不能认为生效；它也不构成整个回合的硬超时。
- 模型代理空闲截断目前设置为零；源码中上游请求等待响应头的读超时未设置，部分流式等待在收到响应头后才进入 watchdog。尚无请求级关联证据证明具体慢调用卡在这一阶段，不应随意缩短线上超时或重试带副作用的任务。
