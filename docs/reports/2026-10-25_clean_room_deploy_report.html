一、验证目的

迁移的价值等于「新机器能不能立起来」，而开发机跑绿证明不了这件事 —— 开发机有历史 profile、有 home 残留、有早就导出的环境变量。本次验证把「一个空 HOME + 本仓源码」 放进容器跑一遍，回答三个问题：

  1. 装得上吗：资产能不能从零落位，且不破坏现场已有的东西？
  2. 是幂等的吗：重复跑会不会重复劳动、会不会把系统改花？
  3. 装上了能用吗：引擎（记忆）在干净环境里能不能真的写入并召回？

四、本次抓出并修复的缺陷

1. 安装器在空机器上以失败退出（真缺陷，本轮修）

  • 现象：安装器把资产全装完了，最后一步却非 0 退出。
  • 根因：人工步骤段（heredoc）里写了 $HERMES_HOME/<...>.env 没做兜底；脚本开头 set -u， 于是没导出该变量的机器上直接 unbound variable 中断。
  • 为什么以前没暴露：开发机上那个变量恰好被导出，永久掩盖了这条路径。
  • 修复：改为 ${HERMES_HOME:-<解析出的目标 home>}；并补两条断言当回归哨兵 （「变量必须已展开」「必须给出凭据文件路径」）。
  • 性质：属"只在我机器上能跑"一类，正是干净室验证存在的理由。

2. 自检脚本里调用了未定义的函数（本轮修）

  • 现象：自检输出里混进一行 log: command not found（不影响判定，但污染证据）。
  • 修复：改成 printf，并重跑确认残留为 0 处。

3. 验证脚本复制业务词表，反被自家门禁抓红（本轮修）

  • 现象：新加的验证脚本里手写了一份业务词表 → 仓级门禁直接红（也会把 CI 弄红）。
  • 修复：验证脚本只调门禁（跑那条门禁测试），不复制词表 —— 词表的单一事实源 就是门禁测试本身。

五、明确不覆盖的范围（不要把绿当全能）

不覆盖 原因 / 归属
网关启停、消息能否收发 容器里没有网关进程、没有平台凭据
模型路由是否可用 容器里没有模型 key；这属于部署后验收
凭据与接入 安装器刻意不碰任何 .env / 凭据；由部署方按运行时说明逐键自建
外部编码执行器的子进程运行时 容器里不装 Node 侧运行时，只验证资产落位与可导入性
业务叠加层 本仓不生成任何业务内容；业务技能源 / 业务工具面 / 业务知识库不在容器里

六、结论

  • 本仓在一个空机器上可安装、可重复安装、装完即可用（引擎端到端成立）， 且不破坏现场已有的身份与配置 —— "clone 一个仓能不能把它原样立起来"这一判据成立。
  • 剩下的差距全在第五节的五行里：它们是「只在盘上、clone 带不走」的部分， 迁移时必须手工补齐（清单见 docs/MIGRATION.md 与业务仓的边界文档）。
  • 每次改安装器或资产清单，复跑 bash docker/verify.sh <ref> 即可回归。
