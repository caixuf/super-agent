一、为什么必须有这一轮

上一轮的干净室只证明了「装得上、装完引擎能用」。这一轮补的是更难的一问： 装出来的东西，各项特性是不是真的成立。第一刀就砍出一个假绿 ——

骨架里根本没有业务叠加层的注入点：{{BUSINESS_OVERLAY}} 只出现在某节的散文说明里。 安装器替换它，等于把叠加层内容塞进那句说明里；生成出来的「生效身份」是坏的，而所有检查都报 PASS。

结论：「文件落位」≠「机制成立」。于是本轮把断言从「装到了吗」改成「语义对不对」。

三、身份注入的判定链（不需要任何可用凭据）

命题：生效身份是否真的进了发给模型的 prompt？ 判定链：

  1. 在隔离 profile 里合成身份（骨架 + 叠加层）；
  2. 用真 provider + 占位/无效 key 打一次调用（不能用「自定义 provider + 死端口」：CLI 在预检阶段 就退出了，根本走不到 API 调用，于是没有转储可判 —— 实测踩过）；
  3. 调用必然失败（HTTP 401）→ Hermes 在 API 出错时无条件写已脱敏的请求转储；
  4. 在转储里断言：骨架独有句 ×3 ✓、叠加层独有句 ✓、生效身份逐字节等于「骨架 + 叠加层」 ✓。

隔离保证（同一次运行里断言）：生产 profile 与顶层的 config.yaml 均无变化； 备份故意保留在不随清理删除的目录，并打印人工 diff -u 命令 —— 「我这次跑不影响你的现场」不是口头承诺，是可复核的断言。

四、本轮修掉的 7 个缺陷

# 级别 缺陷 修法
1 🔴 骨架无注入点（叠加层被塞进散文），而检查报 PASS 骨架新增唯一注入点；安装器替换前断言恰好出现 1 次，否则拒绝合成；检查改为语义断言（骨架原样 + 体积等式 + 标记无残留）
2 🔴 门禁在导出目录里红自己：git archive 不带 .git → git ls-files 失败 → 退化成递归遍历 → 把 pytest 收集阶段写的缓存（内含参数化用例名）当源文件。本地绿、干净室红 门禁显式排除生成物目录 + 生成物判定函数 + 自检测试「生成物目录必须被排除」
3 🔴 执行器凭据解析静默失败：_load_yaml 在解释器缺 PyYAML 时静默返回 {}，上层于是报「解析不到凭据」—— 排障方向直接跑偏 改成响亮失败，点名缺 PyYAML，并给出三条替代来源
4 🔴 补丁 --config 假绿：读不到配置却打 [SKIP] 并 return 0，而它自己的约定是 0=在位 return 2，并区分「缺解析器」与「目录不对」；调用侧必须同时满足「退出码 0」且「输出里真报出键」
5 🟡 地板语义写错：基线会把现场已有的高值改小（实测现场 max_turns=100000） 只抬不降：数值型比较，已 ≥ 地板即不动
6 🟡 新写的检查脚本自己带业务词表 + 硬编码 profile 名（被自家门禁抓到） 改成结构性断言：不写死画像名、不复制词表（等价性用逐字节比对表达）
7 🟡 热删隔离 profile 留下的 WAL inode 被宿主网关持有 → 该 profile 下次启动 profile_parked 不再热删；遇到时换一个新 profile 名；不要停网关（那是生产服务）、不要手删 WAL
