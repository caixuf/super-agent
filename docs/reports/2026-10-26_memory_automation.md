## 2. T3 实施顺序

### 2.1 先锁定身份与路径

1. 复用业务宿主的画像适配层，不能在通用引擎里复制业务身份或代际规则。
2. 确认数据目录、默认 `user_id / agent_id`、向量维度和嵌入后端与历史库相同。
3. 宿主的历史路径兼容语义可能包含“环境路径取父目录”；先读适配实现，不能凭变量名称重构。
4. 同进程服务多 profile 时，全局 `configure()` 不能当成租户隔离。采用每 profile 独立 worker，或先实现明确的每调用配置绑定；不要并发切换全局配置。
5. 不把生产库路径、密钥或用户原文输出到回执；身份审计记录使用可比对的不透明句柄。

### 2.2 对话后只建单

优先用外置 MemoryProvider 的 `sync_turn` 和 `prefetch` 契约；如只做轻量适配，可以使用通用 `post_llm_call / pre_llm_call` 钩子。两种路径选一种，避免同轮两次抽取。

- `post_llm_call` 只将文本和稳定事件标识落入持久队列，尽快返回。
- 幂等键包含 profile、用户、session、turn；不能仅用消息正文或时间戳。
- 不在聊天钩子里同步调用 45 秒的抽取模型，不把延迟重新塞回主会话。
- 模型抽取和向量化由 T2 独立 worker 执行，任务状态有租约、重试预算和结果记录。
- 只有完整成功的回合进入确认事实流程；失败、中断回合可留审计，但不得作为已确认事实自动入库。
- 通用 `on_session_end` 在此版本每轮也会触发，不能当作“用户真正关闭会话”。若在这里提交，必须用 `completed / failed / interrupted` 判定，并按 turn 去重。
- 外部事实、工具输出、模型猜测不能仅凭关键词“决定、必须”升级成已确认用户决策。

### 2.3 独立反思执行

复用 `memory_trigger.run()` 的抽取能力，但先补执行状态判据：当前它可能返回 `ok=True / written=0 / reason=no_fact_extracted`，这既可能是无事实，也可能是 LLM 未注入或不可用，不能一律算成功。

建议区分 `no_decision / no_fact / provider_unavailable / extract_failed / write_failed / committed`。逐事实 `results` 的失败也要纳入回合结果，不能只看最外层 `ok`。

- worker 重启后按租约回收；写入必须可重放。
- `write_fact` 现有事实身份去重可作为基础；发生冲突改写时仍需事件级审计，不能宣称任意重跑恰好一次。
- `flush_background()` 必须汇合后再宣布索引完成，进程死亡前仅“已提交向量线程”不等于可召回。
- 正常通知只发一份任务结果；不要每条事实写入都唤醒主会话。

### 2.4 对话前自动召回

- 根据当前问题调用已配置身份下的 `recall_facts`，沿用现有分数门限、代际和作用域过滤。
- 用事实 ID 去重，限制条数及总字符；建议先以 3 条、1800 字符为隔离测试起点，再测命中率调整。
- 注入的是“检索到的参考数据”，不能放成高优先级指令；正文中的命令和角色声明不自动执行。
- 通过钩子返回 `{"context": "..."}`；临时上下文不要重复持久化到每条聊天消息里。
- 空命中返回空；后端错误独立计数。不得将“查询失败”伪装成“没有记忆”。
- 召回查询若触发外部嵌入，要设超时并验证延迟；不能只做字数限制。

## 3. T3 验收清单

先使用临时目录、离线确定性嵌入和注入的假抽取器，不触碰生产 profile。

| 场景 | 必须留下的证据 |
| --- | --- |
| 明确决策写入 | 稳定事件标识、单条事实 ID、抽取与写入状态 |
| 同轮重复回调 | 事件数量不增，事实不重复 |
| LLM 不可用 | 明确错误分类，消息回复不被阻塞，任务可重试 |
| worker 被终止 | 新进程回收租约，旧 attempt 不能覆盖新结果 |
| 网关被重启 | 由网关外、空闲窗口操作；在途任务与事件仍在 |
| 新会话首轮提问 | 不主动调用记忆工具，发给模型的请求里出现预期 fact_id |
| 无命中 | 无注入；不是空成功包装的错误 |
| 两个用户或 profile | 相同问题不会串出对方私有事实 |
| 失败或中断回合 | 不入已确认事实 |
| 用户活链路 | 用户从真实消息客户端完成“定一条决策→开新会话→问到它”，才可标用户验收 |

验收时使用固定无敏感标记；保存脱敏请求证据，不导出整段用户对话或凭据。

## 4. T7 容量治理先分清对象

存在三个不同问题：`MEMORY.md / USER.md` 的 prompt 字符配额、长期 SQLite 事实库的磁盘占用、单次召回上下文的 token 预算。压缩 gzip 只能减少备份磁盘字节，不能降低 prompt 字符配额；缩短召回也不等于事实库减容。

已有 `tools/memory_budget_report.py` 可在指定隔离或生产 profile 下只读测量：

```bash
python3 tools/memory_budget_report.py --profile-dir <profile-dir> --json
```

注意报告默认缺配置时会使用兜底配额；验收前核对真实配置存在且可解析，避免把兜底值当现网值。

### 4.1 操作顺序

1. 先记录真实字符数、配额、各类记忆数量与待批变更，明确“70% 以下”针对哪个文件。
2. 对 Markdown 做逐字节快照与 SHA-256；对活动 SQLite 用在线 backup API，不能只复制主文件漏 WAL。
3. 备份包含关联标签、身份、来源、置信度、向量和突触账本；在临时目录恢复并验证可读后，才讨论整理。
4. 长期事实库保留可追溯完整记录，短期 prompt 只放活跃索引与高频事实。将冗长条目移出 prompt 前，逐条建立原条目到事实 ID 的映射。
5. 去重必须比较适用代际、主体、条件、来源和时间。相同词句不等于相同语义，更不能用模型摘要覆盖唯一原文。
6. 如走现有待批记忆变更机制，破坏性变更必须绑定 `matched_entry`；旧提案缺绑定时重新生成，不能绕过校验直接重放。
7. 先产候选 diff、覆盖映射、恢复说明，复算字符比例；任何原子事实没有去向就不应用。
8. 真应用后跑召回回归和恢复演练。70% 只是容量判据，必须同时满足信息可寻回和无跨用户泄漏。

### 4.2 不能宣称已完成的情况

- 只做了 gzip 备份，没有减少活跃 prompt 字符数。
- 把配额上限调大，让百分比下降。
- 仅生成总结或删除重复行，没有原子事实覆盖映射。
- 备份存在但没有恢复验证。
- 数据库查询变少，却没有证明身份、路径与过滤条件相同。

## 5. 维护边界与回滚

- 外置插件不直接修改 Hermes 核心；按现有 ABC 和钩子扩展。
- 后台线程如必须在 Hermes 进程内创建，遵循 `agent.memory_provider.spawn_context_thread`，不能裸线程丢失 profile 作用域。独立 worker 则显式绑定宿主画像。
- 禁用新插件只能停止新事件生产；保留队列和备份供审计，不能热删活跃 WAL 或 profile。
- 引擎代码发布、宿主适配、线上启用分三个状态记录。单测通过不能替代启用状态，更不能替代用户验收。

## 7. 记忆系统的分层：先决定什么值得记

| 层 | 放什么 | 权威来源 | 生命周期 |
| --- | --- | --- | --- |
| 原始证据 | 原消息、引用、工具产物、提交与日志句柄 | 不可变证据仓；事实只存链接和摘要 | 依隐私保留策略保存；撤回事实不自动销毁原始审计 |
| 事实与偏好 | 已确认参数、用户显式偏好、适用条件 | 结构化事实库 | 有版本、主体、来源和有效期；用户纠正可撤回 |
| 经验与技能 | 有前置条件、动作、结果和失败边界的可复用方法 | 已验证经验；稳定后进入版本化 skill | 绑定验证环境、版本与复验日期 |
| 任务状态 | 谁在做、attempt、进度、阻塞、回执 | T2 任务库 | 实时变化，完成后归档；不得靠向量记忆判断任务是否已完成 |
| 会话工作集 | 本轮目标与相关证据摘要 | 当前任务和最近对话 | 有界短期上下文，任务边界回收 |

偏好要区分“用户直接说过”和“模型根据聊天推测”。推测只能入候选区。一次回答风格不能自动提升为永久用户偏好。经验不是一段感想，应能回答“什么环境下做什么会得到什么，哪些情况不适用”。

### 7.1 与现有模块的映射

| 已有模块或字段 | 已实现的基础 | 尚缺的机制或核验 |
| --- | --- | --- |
| `memory_kind.py` | technical / personal / context 分类 | 不等于候选/确认，也没有把任务状态从事实中自动剥离 |
| `memory_gate.py` | 代际、可判定性、近似重复门禁 | 未见统一来源可信度、证据版本、有效期门禁 |
| `working_fact` | fact_id、user_id、agent_id、session_id、workspace_id、branch、source、files、fact_link、status、created_at | 字段存在不等于完整赋值；现有写入有默认 session 值，不能当真实消息血缘；未见 first-class expires_at / valid_from / source_revision |
| `fact_tags` | 可存附加元数据 | 用标签挂 TTL 不会自动生效；需要读写和失效流程真正消费 |
| `memory_conflict.py` | 新旧事实判冲突，取代采用 superseded 思路而非直接删除 | 模型判定不等于已验证；冲突应对 reader 可见，自动取代须能审计 |
| `memory_scope.py` | platform / reference / ops 来源性质过滤 | 这是内容类别，不能当用户、群、岗位或任务的访问控制 |
| `memory_trace.py` | 以 fact_id 记录向任务提供过的事实 | “提供过”不等于“正确使用”或“造成成功” |
| `memory_plasticity.py` | 仅处理有 trace 的事实，环境失败不惩罚，连续失败才降级 | 成功相关性不等于因果证据；不能凭任务 PASS 自动认证知识正确 |

### 7.2 候选到事实的最小契约

建议增加显式状态：`candidate → confirmed → suspect / superseded / withdrawn / expired`。这是待实现建议；现有 `active` 不能自动解释为已走完这条审核流程。

每条候选至少携带：主体、断言、适用条件、来源类型、原文引用或哈希、source revision、观察时间、有效起止时间、隐私 scope、抽取器版本、验证状态。模型置信度只表示抽取/判断信心，不替代证据。

- 用户明确决策：绑定消息标识与文字证据，可在用户有权决定的范围确认。
- 工具测量：绑定命令、退出码、环境和产物；只证明当时环境下的测量。
- 外部参考：带 URL、引用、抓取时间和版本，不能直接升级为本地部署事实。
- 推测：保持候选；reader 可按需呈现“不确定”，不得静默当作定论。
- 参数或部署事实必须有版本/有效条件；用户偏好可由直接纠正取代旧版，但保留取代链。

## 8. Scope 是授权规则，不是提示词

需要分别表达用户、岗位、群、项目、任务的读取范围。推荐 reader 先按身份与授权过滤，再做向量排序；不能先检索全部再指望模型不泄漏。

- 私人偏好默认仅用户可读；岗位经验只有获准共享的部分能进入岗位库。
- 群事实只在该群允许范围内可见；从群转私聊不能自动带出其他参与者资料。
- 任务临时证据随任务授权；共享 workspace 不等于所有 agent 可读所有文件。
- 明确共享范围交集和优先级：例如用户确认仅某项目生效的偏好，不覆盖跨项目默认值。
- 无身份/无授权元数据时 fail closed，或只允许已明确公开的通用参考库。

现有 `user_id` 查询过滤提供一部分基础，`agent_id` 字段和 `scope` 标签本身没有证明这些 ACL 已实现。上线前用两个用户、两个群、两个 profile 的交叉反例验证。

## 9. Reader 质量、冲突和撤回

reader 的目标不是“每次都能召回”，而是“在预算内给正确、适用、可引用的证据”。按以下顺序执行：授权过滤 → 状态/有效期/版本过滤 → 检索与重排 → 冲突分组 → 有界注入。

预算同时限制条数、字符/token、查询耗时、嵌入和重排费用。低于相关性门限宁可不注入；超时明确降级，不悄悄扩大全库范围。一个事实只注入一次并记录 fact_id、版本、task_id 和查询时间。

新旧规则冲突但尚无足够证据确认取代时，应呈现“旧版本依据 A；新候选依据 B；适用版本未确认”，并询问或验证。不要按“新写入”“召回分高”自动胜出。

撤回必须是写路径的一等操作：停用事实、保留版本链、清除或失效缓存与检索索引、让派生经验可追溯到被撤回来源。原始证据和撤回原因按访问控制保留；涉及用户删除要求时按隐私策略处理，不能以审计为由无限保留。

## 10. T7 的“无损”如何定义

- **字节无损压缩**：gzip 等可恢复完全相同字节，核验 SHA-256；减少磁盘，不减少解压后的 prompt token。
- **结构化整理**：移出活跃 prompt、去精确重复、建立事实索引；要求每条原始条目有稳定去向及访问权限，不等于已经减少长期事实库总量。
- **语义摘要**：本质上有丢失条件和细节的风险。不能直接称“无损”；原文必须保留，可逆链接和原子事实覆盖测试是最低要求。

T7 的可交付口径应改成：“活跃 prompt 占用低于 70%，原始证据完整可恢复，关键事实召回回归无下降，权限隔离不退化”。若仍坚持语义上绝对无信息损失，则不应以自由生成摘要作为唯一存储。

## 11. 真实评测与必须通过的反例

用版本化小型金标集先测，按真实任务扩充，训练/调参样本与验收样本分开。分别报告 writer、reader、端到端表现，不用“库里多了几条”代替质量。

| 指标 | 如何测 |
| --- | --- |
| 写入精确率 | 已入确认库的事实中，来源确实支持、主体和条件正确的比例 |
| 写入召回率 | 金标明确决策中，自动流程正确捕获的比例 |
| 证据完整率 | 带可定位来源、版本、适用范围的事实比例 |
| 检索质量 | relevant recall@k、precision@k、错误代际/过期/越权命中数量 |
| 冲突处置 | 不确定冲突是否被呈现；已取代旧事实是否仍被当有效答案 |
| 端到端收益 | 相同问题，开关记忆后答案正确性、引用、延迟和成本变化 |
| 恢复与撤回 | 崩溃重放是否重复、撤回后是否仍可在提示或缓存出现 |

必须纳入反例：用户在提问而不是拍板；否定句；引用他人命令；网页中的 prompt injection；同名不同人；相同参数不同代际；旧版本与新版本；临时偏好；模型自称“已验证”但无产物；工具执行失败；环境故障导致任务失败；相似但条件不同的经验；用户撤回；跨群或跨用户同问句；压缩前被保留、压缩后被漏掉的例外条件。

阈值应由实际金标基线确定。安全性反例要求越权泄漏为零；其它指标先公布基线和样本数量，不在未测时编造通过率。
