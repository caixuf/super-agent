# 业务适配与运行状态一致性修复计划

本计划补充 `docs/DEPLOYMENT_CLOSEOUT_PLAN.md`，解决“通用仓库有能力，但业务机器人实际行为不一致”。它是后续实施指导，不表示代码、验收或部署已经完成。开发和主动测试只使用本机 caixuf 的隔离 profile；远端实例上仅做已授权的只读调查，真实消息由用户手动发送。

## 目标与原则

把一个机器人拆成三份明确的东西：Super Agent 通用核心、业务适配包、某个实例的部署配置。主 Agent 默认是完整能力体；只有任务适合拆分时才使用同事。长期记忆可按授权共享，成员的会话历史保持隔离。

运行时要能回答：**期望安装了什么、磁盘上是什么、进程实际加载了什么、功能是否真的可用**。这四种状态必须分开；无法观察到进程内部时显示“未知”，不能用文件哈希冒充已加载版本。现有身份、记忆和业务配置均不得在核对时覆盖。

## 已观察到的问题与待证实部分

- 10 月 30 日只读核对：本机与远端实例的源码仓库均指向 `8892425`；业务 profile 仍有独立 SOUL、业务 AGENTS、插件副本和运行服务。身份规则多处维护，且部分派工表述存在不同侧重；具体对某次回答的影响尚未证明。
- 业务 日志中实际出现 localvec 召回子进程退出码 2，诊断为 `backend_query_failed / RecallUnavailable`，但召回服务仍显示 active。具体后端故障尚未查明，不能凭服务存活判断召回成功。
- 观察到约 34.3 万输入 token 的调用、一次压缩摘要截断后恢复、完成回执延后和积压。它们是值得处理的事实，不自动证明某条回复失误的根因。
- 现场配置修改时间晚于网关启动时间；是否已热加载需要逐项核验。插件存在于 enabled 列表也不等于其独立的 `settings.enabled` 已打开。
- 上述均为特定时点观察，实施时应重新核对版本和状态。现有报告中对尝试令牌清理能力的过强表述不作为安全证明。

## 第一阶段：先让差异看得见

**改动位置**：在 `checks/` 或现有运维入口新增只读实例诊断；复用 `checks/feature_check.sh`、`checks/identity_injection_check.sh`、`checks/model_context_check.sh` 的相关能力，避免再造独立配置体系。

1. 对指定 profile 输出脱敏报告：Super Agent 与 Hermes 版本；业务适配包版本；SOUL、AGENTS、插件与关键配置的路径及摘要；插件列表、各自总开关；配置文件修改时间、进程启动时间和进程能够自报的已加载版本。
2. 每一项分列“期望 / 磁盘 / 运行中 / 功能探测”，状态只使用一致、不一致、未知、未启用及失败等可解释结果。仅以修改时间发现可能待重载；不得推断所有配置都需要重启或已经生效。
3. 只读能力探针先覆盖记忆服务健康、单次合成召回、工具可发现性、模型路由和回执积压。探针默认不发消息、不执行用户任务、不写生产库；健康探针失败需区分“失败”和“没有匹配结果”。需要访问真实消息平台的项目由用户手动触发。
4. 本机隔离环境构造旧插件、关掉设置开关、配置变化未加载、召回失败和不可观测等情况，验证诊断不会误报通过。报告不输出密钥、会话正文、记忆内容或敏感路径参数。

**完成标准**：一份报告可以准确指出已知漂移，不能核验的项明确标未知；同一份检查在旧 profile 上只读运行，不改变任何状态。

## 第二阶段：制定业务适配契约

在通用仓库定义版本化清单与最小示例，在业务侧提供对应实现。先给出清单和验证器，再改安装器；不要为 业务 定制一套独立调度器。

清单至少声明：适配包 ID 和版本、兼容的 Super Agent/Hermes 版本范围、业务身份叠加文件、业务工具或 MCP 的名称和启用条件、模型逻辑角色、记忆适配器与身份映射、插件需求、必需凭据的名称以及受限工作区。凭据值只留在目标环境。

规则边界：核心层拥有任务归属、交付结果、权限和安全等不可被业务文本覆盖的程序约束；业务层提供领域知识、岗位、工具与业务流程。对“何时派工、何时查技能”等行为偏好，只保留一个清晰的优先级和可解释默认值，避免多份 SOUL 用绝对语气重复下令。业务叠加不能凭声明获得工具权限。

**完成标准**：提供通用示例和本机合成业务适配样例；无凭据、版本不兼容、字段冲突和缺失工具均有明确诊断；不包含 业务 业务秘密。

## 第三阶段：身份组装与更新

1. 复用 `identity/SOUL.generic.md`、`identity/overlays/` 和 `install/install.sh --compose-soul`，将通用骨架、业务叠加、实际 SOUL 的来源和版本记录在可审计清单中。业务 AGENTS 的用途单独声明，避免把它误当成通用身份的一部分。
2. 增加预览：展示将使用的来源、摘要、规则差异和将改变的文件；用户编辑过的现场内容不能自动覆盖。支持配置不变时幂等，升级冲突时停止并给出人工可读差异。
3. 在隔离 profile 演练升级和回退，确认业务知识、权限及核心纪律均保留。新增/更新骨架后需明确哪些变更进入新回合、哪些需要重载；用实际运行测试证明，不靠猜测。

**完成标准**：业务身份可从受控输入重新生成并审阅；重复安装不产生额外改动；现场手工变更不会静默丢失。

## 第四阶段：功能适配和真实问题修复

- **记忆**：先在本机模拟 `RecallUnavailable` 和召回故障，追踪调用方、socket、服务状态和后端视图的错误链；故障应向运行时报告不可用，而不是空召回。针对远端实例的具体故障继续只读取证，不在该机器做开发测试或直接修改记忆库。真实根因确认后再制定修复与恢复方案。
- **长任务和交付**：复用现有 `task-progress`、`durable-dispatch`，核对同一任务的会话归属、进度、终态和交付；积压可诊断，不擅自重发或修补历史回执。
- **同事**：保留现有派工入口及默认完整 Agent 原则。真实 Hermes 执行的生命周期、成员创建与退出证据未验通前不标记为生产可用；不得用环境变量扫描空结果证明共享 Gateway 后台工作已结束。
- **上下文**：度量 token、压缩触发与输出是否进入下一轮；模拟截断、失败和回退。评测应同时观察任务正确率与延迟，不能把更大上下文或更早压缩当作自动修复。

**完成标准**：每条链路分别有本机隔离测试、失败模式和明确的开关；未验通的能力显示不可用，不阻塞已验通的单 Agent 基础功能。

## 第五阶段：部署、验证和回退

1. 在本机隔离 profile 用真实安装路径演练：读取清单 → 检查依赖 → 预览差异 → 安装 → 按实际需要加载 → 运行只读诊断。明确正在运行的任务、备份、重启和回退边界。
2. 将验证结果与当前版本绑定，列出实际运行版本、启用能力、跳过项和风险；真实进度卡、连续对话、附件及业务结果必须由用户手动测试，不能由离线探针替代。
3. 对远端实例制定可审阅的单独变更清单、备份和回滚方案，在本机门槛通过后选择维护窗口；不同时开启新旧派工或投递链。回滚需恢复版本和配置并核实服务，不能声称没有经过演练就零数据损失。
4. 保留凭据在现场，不将状态库覆盖当作普通回滚；记忆压缩、数据迁移及历史回执修复需要各自的证据和恢复方案。

**完成标准**：本机安装与回退可复现；目标实例经过用户参与的真实验收后才标记部署成功。若能力未达标，单独关闭并记录后续工作。

## 最后阶段：一键部署与 Docker 干净室

等预定能力和业务适配完成后，再把清单、安装、版本钉选、插件、补丁、无密钥凭据引导、诊断和回退组合成一键交付。用干净环境逐项验证，再跑 Docker；说明 Docker 与现场网络、GPU、消息平台和存储的差异。脚本全绿不等于业务任务质量已经通过。

## 建议执行顺序

1. 只读实例诊断和本机故障复现。
2. 适配契约、身份组装与漂移检查。
3. 分别修复记忆、长任务/交付、同事运行中实际发现的问题。
4. 本机隔离部署及回退演练，再安排目标实例的部署验收。
5. 所有功能收尾后，完成一键部署与 Docker 干净室。
