# 同事转交消息：字面显示与平台适配检查

当前不能把普通 `text` 消息当作严格的字面文本。平台[发送消息内容说明](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json)明确列出：`text` 中的特定标签可以触发提及，也支持部分样式和链接。因此，即使底层请求指定 `msg_type=text`，也不能证明不可信摘要会原样显示或不会触发提及。尚未找到足以证明严格字面显示的官方转义约定。

现有宿主适配器的公开发送方法会根据内容选择 `text` 或富文本；内部方法可以显式指定 `msg_type`，但它是私有接口，未来版本可能改变。现有通用发送器没有声明本功能所要求的字面文本能力。不能只加一个能力标记就视为验证通过。

## 已做的离线检查

`tests/test_colleague_literal_text_real_host.py` 在显式指定的真实宿主适配器上，用内存假对象替代所有平台调用，验证了以下行为：

- 普通文本中的提及标签被原样放入发送请求；是否真正提及由平台决定。
- 常见 Markdown 内容会被公开发送方法选择为富文本。
- 超长文本会拆成多个请求，并沿用传入的同一操作 UUID。现有后台直发先检查长度并拒绝拆分；新接线也必须保留这个约束，或为每一段设计独立的去重与回执。
- 宿主的长度检查按字符计数，不等于编码后的字节数。实测 8000 个表情可以通过字符限制，但仅文本的 UTF-8 JSON 已超过 30 KiB；平台的[通用错误码说明](https://open.feishu.cn/document/server-docs/api-call-guide/generic-error-code)列出消息大小限制，接线时还要限制编码后的请求大小。
- 回复目标失效时，普通聊天会回退为新消息；有话题标识时不会回退为顶层消息。回复关系和用户预期需要单独验收。
- 底层遇异常时会在同一操作中重试，并继续传递同一 UUID。超时可能发生在服务端已经接收之后；仅有本地测试不能证明平台端去重结果。

2026-10-27 在一次性临时目录中，使用宿主解释器对实际适配器运行了以上离线检查，结果通过；测试不建立真实连接、不发送消息。适配器源码 SHA-256 为 `a02deffe5f525fc3b0591dc6d11c26b9b876cd3663e6353fa2ce8397c0707cc5`；路由工具源码 SHA-256 为 `e6597886b00221b03015362c48d814d5841550c7febff3189b78fa1ebe442f89`。这只代表该版本的本地代码行为。

## 接线前还要验证

1. 找到平台明确支持的无提及、无格式解释的发送方式，或者设计并验证一种有损但明确告知的安全展示方式。不能假设 HTML 转义或换用消息类型就一定有效。
2. 使用单独测试环境验证特殊字符、提及标签、样式、链接与超长文本的实际显示，以及是否触发通知；验证方式需由用户或管理员按授权执行。
3. 继续沿用宿主的会话归属和收件人检查、唯一回填方、每次发送的持久日志、真实消息回执和不明状态停放。附件只能发送经过批准并从所属任务执行目录快照的文件。
4. 验证普通聊天与话题的回复行为、断网/超时后的回执恢复、重复调用和宿主升级后的接口兼容。

在这些验证完成前，不应给当前发送器声明字面文本能力，也不应启用同事署名的真实平台回填。
