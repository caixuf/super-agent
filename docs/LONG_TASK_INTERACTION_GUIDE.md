# 长任务交互优化：执行指导

## 想达到什么效果

用户交给机器人一项几分钟甚至更久的工作后，应当能一直看懂它在做什么，也能继续说话、补充要求或暂停任务。完成后，用户能在原来的对话中找到结论和文件。

第一版只需要打通一条完整路径：**一位用户发起一个长任务，途中询问或调整，最后在原会话收到结果。** 先把这条路做可靠，再扩展多同事和复杂编排。

用户看到的体验可以是：

```text
任务：分析项目架构
状态：正在读取源码
已完成：定位入口、梳理主要模块
下一步：核对模块间调用关系
最近更新：13:42
```

这只是显示样例。阶段、进度和时间必须来自实际任务事件；没有可靠依据时显示“正在处理，暂无新进展”，不要编造百分比、完成时间或下一步。

## 阶段零：先把调度查清楚

交互优化不能只改卡片。先检查并测试长任务从接收到最终回执的整个调度路径，写出每一步的唯一负责人：**接收 → 持久入队 → 领取 → 执行和心跳 → 等待/续跑 → 完成 → 原会话回传**。不清楚实际入口、队列和运行进程前，不启用第二个调度器或新回填线程。

当前代码提供了基础机制，但尚不能由此断言所有长任务调度都可靠：

- `Pool` 持久化任务、租约、尝试次数和回执；领取按创建时间遍历，未就绪的依赖会被跳过。这不是跨多个岗位队列的全局公平或严格完成顺序保证。
- `Worker` 按实例限制执行槽位，FlowCoro 是可选执行后端；多个进程或多个岗位队列的总资源、模型并发与对话资源是否互相挤占，需要现场盘点和测量，不能从单个 worker 上限推断。
- `Pool` 区分允许重放与不允许重放的任务；当前 `durable-dispatch` 的只读分析入口使用 `replay_safe=True`。如果扩展到写代码、外部发送或其他有副作用的任务，不能原样沿用这个判断，必须逐类验证幂等和恢复策略。
- 运行中进程锁、心跳、attempt 标识和取消有现成机制与测试；进程启动后、登记前等异常窗口仍需按 `docs/POOL_RUNTIME.md` 的边界处理。协程工具的取消是协作式的，取消请求不等于工具已停止。
- `SessionExecution` 需要宿主实现准入和提交权威；Hermes Goal 有自己的会话状态与续跑机制。是否在真实链路中形成一个完整闭环，必须通过真实接线验证。

### 要做的调度审计与验证

1. **任务分类与准入**：列出只读分析、写入工作、外部调用和物理资源任务分别由谁接收、使用哪个队列、是否允许重放、有什么并发和时间限制。业务侧物理资源的原有权威调度不可被绕过。
2. **排队与资源竞争**：在隔离环境持续提交长任务和短任务，分别测量入队等待、领取时间、执行时间及主对话响应；检查是否存在长期饥饿、一个岗位占满资源或某个等待依赖阻塞无关任务。当前没有测量前，不把这些风险说成已经发生。
3. **跨会话与容量**：同一用户连续发起任务，两个用户同时发起任务，多岗位共享宿主时分别测试。核对用户和会话归属、队列上限与过载反馈；执行容量满时不能默默丢任务或让聊天请求无限等待。
4. **取消与超时**：覆盖排队中取消、启动途中取消、执行中取消、接近完成时取消及进程无响应。核对取消确认、实际进程状态、终态和回执是否一致；协作式工具不响应取消时要如实报告。
5. **崩溃与恢复**：分别在入队后、领取后、进程启动后、执行完成后以及发送后确认前中断。观察锁、租约、attempt、外部副作用与回执；只读且可重放的任务按策略恢复，有副作用或结果不明的任务先核实，不重复执行。
6. **Goal 与队列的关系**：为每项任务固定唯一的续跑负责人和执行会话。状态落盘后才安排下一步；后台等待由进程或任务事件唤醒，避免 Goal 续跑、进程完成通知和队列回填各自触发同一轮工作。
7. **数据和证据**：记录提交、开始、心跳、状态变化和完成/送达的时间与原因；分别统计排队、模型执行、工具、Goal 判断及平台投递耗时。先用基线和真实场景制定响应目标，不凭感觉把超时简单调大。

**阶段出口：** 有可复现的调度链路图、每类任务的重放和资源策略，以及上述场景的测试记录。真实平台没有验过的项目标为未验；发现缺陷先修其根因，再推进体验展示。

## 按阶段实施

### 阶段一：任务状态和单一展示入口

**目标：用户知道发生了什么，消息不再散落。**

- 用户创建长任务后立即得到任务号和一个进度入口。优先更新同一张任务卡；平台或当前会话不支持时，明确采用兼容展示，不假装一直是同一卡片。
- 用现有账本和 worker 事件展示：已接收、排队、执行中、等待用户、已完成、失败或取消。区分“发出取消请求”和“确认已停止”。
- 记录最近有证据的阶段、更新时间、可用产物和错误摘要；进度没有数据就不显示百分比和预计时间。
- 中间事件合并展示，避免每条工具输出触发新消息或模型续跑。只对需要用户处理、失败和最终结果做必要提醒。
- 卡片更新超时或响应丢失属于结果不明：保存可核对的信息，先查询或核对回执，不立即重发另一张。把“任务完成”和“消息已送达”分开记录。

**阶段验收：** 隔离环境完成一个长任务，人工能在同一入口看到接收、至少一个真实进度变化、终态和结果；没有无依据的进度或连续刷屏。模拟卡片超时、重试和重启，检查不丢终态、不盲目重复发送。

### 阶段二：主对话和任务执行分开

**目标：长任务干活时，用户仍能问进度、补充要求。**

- 主 Bot 创建独立任务会话，并在适配层持久绑定任务 ID、用户、原会话、回传路由、执行会话和对应 Goal。主会话收到可靠的创建回执后结束当前回合。
- 主会话对“进度”“暂停”“继续”“取消”等控制优先走明确的状态或控制入口；不要每次为查状态启动新的长模型工作。自然语言识别和短回复可按现有宿主能力处理，不要把模型猜测当作控制动作已完成。
- 补充要求按原任务和用户身份送达；执行中的步骤在安全边界接受调整。清楚告诉用户“已收到”“正在应用”或“已应用”，不能声称已经改变正在进行的不可撤销操作。
- 用户消息优先于自动续跑，但不要承诺已运行模型回合能被瞬间抢占。使用独立会话减少前台等待，并实测真实响应时间。
- 防止重复创建：同一请求有稳定标识；并发重试、网关重启和重复回调要检查既有任务与会话。跨数据库操作按实际能力设计恢复，不能把两次写入说成原子事务。

**阶段验收：** 在长任务运行时连续询问进度、补充要求，并测试暂停/恢复；主对话能回应，要求送到正确任务。两个独立会话同时发任务时，状态、上下文、结果和文件互不串用。同一任务的重复提交不会变成两份实际工作。

### 阶段三：可靠续跑与结果回传

**目标：重启可恢复，完成后有且只有一个可核验的交付结果。**

- Goal 的目标与完成条件由宿主持有；重启后先读取真实任务、Goal 和进程/worker 状态，再决定继续、等待、暂停或要求处理。
- 后台任务执行用现有持久队列与租约；等待外部任务时使用已有完成事件或受控等待，不靠反复唤醒模型查询。
- 已完成且有副作用的步骤不能因为重启被当作新步骤盲目重跑。结果不明的步骤要先核实；无法核实时保持待处理并说明原因。
- 指定唯一的最终发送方。完成、失败和取消都要有清楚终态；附件要核对真实文件、权限和实际上传结果。拿到匹配的送达回执才确认投递。
- 保存提交时可信的用户与路由；无路由或路由无法证明时保留结果待查，不发送到“当前活跃会话”。不要为了清理积压删除证据或补猜路由。
- 同卡更新、文件上传和消息回传分别核实；更新卡片成功不等于附件已经送达。

**阶段验收：** 分别模拟进程退出、worker 崩溃、网关重启、发送后回执丢失和用户暂停。检查没有重复执行、串会话或盲目重复发送；最终报告说明已完成、失败和仍需处理的部分。

## 测试与交付

1. 先补与改动对应的回归测试。可从仓库现有 `tests/test_session_execution.py`、`test_liveness*.py`、`test_task_status*.py`、`test_durable_dispatch*.py`、`test_longtask_guard.py`、`test_card*.py` 和 `test_completion_delivery.py` 选择相关用例；新行为必须有能发现错误的测试。
2. 在隔离环境复核顺序、幂等、越权、暂停/取消和不明回执。测试必须使用临时状态目录，不能污染运行中的账本。
3. 跑仓库要求的 `bash verify.sh`；记录通过、失败和跳过的具体原因。上游宿主或可选依赖不可用时，明确写未验证，不能把跳过写成通过。
4. 做一项真实但只读的源码分析：用户手动发送任务，途中再发送进度询问和补充要求，最后人工核对同一卡片或约定的兼容展示、结论和文件。测试前确认目标 profile 和测试会话，避免影响其他进行中的任务。
5. 报告基线与改后数据：收到确认耗时、进度可见情况、插话响应时间、消息条数、最终送达与文件结果。区分模拟测试、真实模型、真实消息平台三种证据；没有测到的写“未验证”。
6. 把通用能力、安装入口、升级说明和测试留在本仓。现场地址、权限和凭据由部署配置提供；真实业务动作继续使用其原有权威入口。最终一键部署与 Docker 干净环境验收放在所有功能完成后的最后阶段。

## 完成的定义

不能只看“代码已写”或“测试数量增加”。用户应能在同一个对话中发起任务、看见可信进展、继续交流、暂停或调整，并在任务结束后找到一次可靠交付的结论和文件；同时，任务归属正确、重启后不乱跑。未达到的项要逐条留在交接记录里。
